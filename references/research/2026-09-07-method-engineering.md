# Prior art: method engineering, process tailoring and configurable processes for redkiln's activity engine

Date: 2026-09-07. Scope: academic + standards prior art for the design question "can each ACTIVITY in a per-stage catalog carry self-contained applicability rules (required inputs, produced outputs, dependencies, weights/conditions) so a deterministic engine — not an LLM — builds the activity DAG per work item from its classification and the artifacts that already exist?"

Evidence tags: `[documented]` = read in the cited source; `[inferred]` = my synthesis/reading between the lines. Redkiln vocabulary: work item = initiative/project/story/bug/incident/spike; stage = triage…closeout; activity = catalog entry inside a stage.

Executive verdict (details in "Direct answers" at the end): there is strong, thirty-year-deep precedent for exactly this shape — Essence activity spaces with Alpha-state entry/completion criteria, SME method chunks with situation/intention interfaces, Provop/C-EPC context rules, V-Modell XT rule-driven tailoring — and equally strong evidence about why the heavyweight incarnations died (authoring cost, one-to-one variability, no closed feedback loop, tool-bound content). The literature is unanimous that tailoring *criteria* can be enumerated but that the *consequences* of criteria have mostly been left to expert judgement; the systems that made tailoring deterministic did so by (a) restricting the rule language and (b) letting the rules bind to *observable facts* (artifact exists, project type, criticality band), not to open-ended judgement.

---

## 1. OMG SPEM 2.0 and Eclipse Process Framework (EPF) Composer / OpenUP

**What it modeled.** SPEM 2.0 (OMG formal/2008-04-01) separates *Method Content* — Roles, Tasks, Work Products, Guidance — from *Process* — Activities, Capability Patterns (reusable process chunks), Delivery Processes (end-to-end lifecycles) — via "descriptors" that reference content elements and can locally override them. A Task is associated with input and output Work Products; a Process is a sequence of tasks performed by roles that makes explicit how work products are created and evolve. `[documented]` https://www.omg.org/spec/SPEM/2.0/PDF , https://modeling-languages.com/process-software-modeling-spem/

**Selection/tailoring mechanism.** Two mechanisms: (1) *Method Plugins* package content and processes; a *Method Configuration* is a subset of plugins/packages selected for publication — configuration is by inclusion/exclusion of packages, not by rules. (2) *Variability* on content and process elements with four types: `contributes`, `replaces`, `extends`, `extends-replaces`; resolved top-down from base, contributes first, then replaces, extends last. `[documented]` https://www.ibm.com/docs/en/engineering-lifecycle-management-suite/lifecycle-optimization-method-composer/7.6.2?topic=variability-extends-replaces . SPEM 2.0 has no first-class notion of *conditions* under which a task applies — applicability lives in prose Guidance or in a process engineer's choice of configuration. `[inferred from spec structure]`

**What worked.** The content/process split is genuinely good: one catalog of tasks with declared work-product I/O reused across many lifecycles; capability patterns as reusable sub-DAGs; the "descriptor overrides content" idea (a stage can locally change a task's optionality) is exactly what a per-stage rubric needs. Tool support (EPF Composer, IBM Rational Method Composer) published navigable HTML method sites. `[documented]` https://en.wikipedia.org/wiki/Eclipse_process_framework

**What failed.**
- Variability is one-to-one: "the content variability capability severely limits users to one-to-one mappings. Processes trying to integrate various aspects may require block-copy-paste style clones." `[documented]` https://en.wikipedia.org/wiki/Eclipse_process_framework
- Adoption never happened: Steghöfer's 2019 experience report states SME and SPEM "have never reached broad adoption… high-quality descriptions… modelled in SPEM are few and far between… the EPF project used to publish descriptions of Scrum, XP and the OpenUP, but the downloadable content is outdated… there is little support for combining different practices… into new processes or tailoring the method content." `[documented]` https://ceur-ws.org/Vol-2308/isee2019paper02.pdf
- EPF termination review (successful, 20 July 2022): "IBM has been the only contributor… in recent years. IBM is moving away from rich client-based method authoring to web-based method authoring using DOORS Next, and so plans to discontinue contributing." The project is archived. `[documented]` https://projects.eclipse.org/projects/technology.epf/reviews/termination-review , https://projects.eclipse.org/projects/technology.epf . IBM's commercial fork survives as IBM Engineering Lifecycle Optimization – Method Composer 7.6.x (GA Dec 2020). `[documented]` https://www.ibm.com/support/pages/ibm-engineering-lifecycle-optimization-method-composer-76
- Root causes `[inferred]`: (i) the output was *documentation for humans*, never an executable artifact, so nothing consumed it in the loop; (ii) authoring cost was enormous relative to payoff (MOF/UML-based metamodel, XMI, specialist tools); (iii) selection was by manual configuration of a giant library, which doesn't scale to per-project, let alone per-work-item, tailoring; (iv) content rotted because no runtime validated it.

**Steal this for redkiln.**
- Keep SPEM's split: `catalog/` (method content: activity id, inputs, outputs, guidance) vs `stages/` (process: which activities a stage references, with per-stage *descriptor overrides* — required/optional/skip, weights).
- Adopt `contributes/replaces/extends` as the extension vocabulary for tenant/project overlays on the base catalog, with SPEM's deterministic resolution order (contributes → replaces → extends). It is small, well-defined, and already implemented at scale once.
- Do NOT adopt: a MOF metamodel, XMI, or "method configuration by package selection". The engine consumes the catalog; the catalog is not a document product.

## 2. OMG Essence / SEMAT kernel — closest fit

**What it modeled.** Essence 1.2 (OMG formal/18-10-02, Oct 2018) = a *Kernel* + a *Language*. Kernel: seven Alphas ("Abstract-Level Progress Health Attributes": Opportunity, Stakeholders, Requirements, Software System, Work, Team, Way of Working), each with an ordered set of *states*, each state defined by a *checklist* ("Alpha States can be concisely and accurately defined in terms of the set of Checklist Items that need to be achieved for the State to be achieved"); 15 *Activity Spaces* ("placeholders for something to be done"; e.g., Explore Possibilities, Understand Stakeholder Needs, Shape the System, Implement/Test/Deploy the System, Prepare to do the Work, Coordinate Activity, Track Progress); and *Competencies* with levels 0–5. Practices supply concrete Activities and Work Products; a Method = Kernel + Practices. `[documented]` https://www.omg.org/spec/Essence/1.2/PDF (§4, §8.1), https://www.ivarjacobson.com/essence-explained-agile-tools

**The key mechanism — Alpha states as typed pre/postconditions.** Every kernel Activity Space is specified with `Input`, `Entry Criteria`, and `Completion Criteria` expressed as `Alpha::State` pairs, e.g. `[documented]` (spec §8.2.3):
- Explore Possibilities — Input: none; Entry: none; Completion: `Stakeholders::Recognized, Opportunity::Value Established`.
- Understand Stakeholder Needs — Input: Stakeholders, Opportunity, Requirements, Software System; Entry: `Stakeholders::Recognized, Opportunity::Value Established`; Completion: `Stakeholders::In Agreement, Opportunity::Viable`.
- Ensure Stakeholder Satisfaction — Entry: `Stakeholders::In Agreement, Opportunity::Value Established`; Completion: `Stakeholders::Satisfied for Deployment, Opportunity::Addressed`.
- Use the System — Entry: `Stakeholders::Satisfied for Deployment, Opportunity::Addressed`; Completion: `Stakeholders::Satisfied in Use, Opportunity::Benefit Accrued`.
The language metamodel makes this general: `ActivitySpace` and `Activity` both own `Criterion` objects, subclassed `EntryCriterion` / `CompletionCriterion` (spec §9.3.4.9–11), each pointing at an Alpha State or a Work-Product Level of Detail; Activities may create/read/update/delete Work Products and Alphas. `[documented]` spec §9.3.4; OMG issue tracker discussion at https://issues.omg.org/issues/lists/essence-rtf?view=ALL ("the states currently listed as completion criteria in a kernel activity space are those states to which various alphas may be progressed by activities considered to be within the activity space").

**Dynamic semantics — the spec explicitly targets a "what next" engine.** "At any point in time in a running software engineering endeavor, the method can be consulted and it will return advice on what to do next. Moreover, the method can be tweaked at any point in time and will still return (possibly alternate) advice." `[documented]` spec §7.4. Practice conformance Level 3 ("Practice Actionable and Trackable") requires "an Alpha with a fully defined state machine with a complete set of checklists… and all activities… clearly related to the Alpha state progressions that they enable", enabling tools to do "real-time alpha state tracking, task generation, pattern matching, and completeness checking." `[documented]` spec §2.2.4. State assessment is non-monotonic: "Each time you reassess a state, if you do not meet all the checklist items, you can go back to a previous state." `[documented]` spec §8.1.4. Commercial tooling (IJI "Essence WorkBench") advertises exactly this: "guides you on what to do next if you know where you are." `[documented]` https://www.ivarjacobson.com/essence-explained-agile-tools

**What worked.** Shared vocabulary; the Alpha-state checklists are practice-independent and small (7 alphas × ~6 states × ~4–6 items); the games (Progress Poker, Checkpoint Construction, Milestone Mapping) give humans a fast way to *assess* state; practices compose because they all progress the same alphas. Classroom studies (450+ students) and the 2019 report confirm the cards/checklists are the part people actually use. `[documented]` https://arxiv.org/pdf/1809.08827 , https://ceur-ws.org/Vol-2308/isee2019paper02.pdf

**What failed / limits.**
- The *language* (metamodel, XMI, Level-2/3 practices) has the same authoring-cost problem as SPEM; students "struggled with the idea of a language to describe processes" and "how to make the activity spaces more concrete by defining suitable activities within them." `[documented]` ceur-ws Vol-2308 paper.
- Checklist *evaluation* is human judgement ("Stakeholders: In Agreement" is not machine-decidable). Essence gives you the *type* of the precondition, not a decision procedure. `[inferred]`
- Kernel activity spaces are lifecycle-generic; Essence does not classify *work item kinds* (bug vs initiative) — it expects practices to do that. `[inferred]`
- No widely used open runtime that actually executes "task generation" from Level-3 practices; the value stayed in cards and in one vendor's tools. `[inferred]`

**Steal this for redkiln.**
- Model each activity as `{inputs: [WorkProduct@LevelOfDetail | Alpha::State], entry: [...], completion: [...]}`. Entry criteria *are* the applicability rule; completion criteria *are* the skip rule ("this initiative already has a competitor analysis" = `Opportunity::Value Established` evidenced by an artifact). This is Essence's design, verbatim, and the reason it fits a deterministic engine is that criteria are *typed enumerations*, not prose.
- Replace human-assessed checklists with **machine-decidable evidence predicates**: a checklist item = an artifact exists with required frontmatter/sections, a test passes, a review verdict is recorded. Keep Essence's non-monotonic semantics: a state can regress when evidence is invalidated (artifact deleted, spec changed after design).
- Use Essence's per-alpha *state ladders* as the backbone of the per-stage rubric: a stage's exit = a vector of required Alpha states; the engine picks activities whose completion criteria cover the missing states (set-cover over a small lattice — cheap and deterministic).
- Adopt Level-3 conformance as a **lint rule** for the catalog: every activity must name at least one state it progresses; every stage exit state must be reachable from some activity; otherwise the catalog fails validation.

## 3. Situational Method Engineering (SME), OPEN Process Framework, method rationale

**What it modeled.** Brinkkemper (1996) defined method engineering as "the engineering discipline to design, construct and adapt methods, techniques and tools for the development of information systems" and SME as project-specific construction by assembling reusable *method fragments* (product fragments + process fragments) from a method base. `[documented]` Information & Software Technology 38(4), 1996 — summarised at https://www.researchgate.net/publication/220349352_Situational_Method_Engineering_State-of-the-Art_Review . Ralyté/Rolland refined *method chunks*: a chunk = body (process + product parts) + **interface** = `<situation, intention>` where situation is "the pre-condition for usage" (required input products) and intention is "the post-condition of the use of this chunk" (the goal it achieves); a *descriptor* adds reuse context (application domain, design activity, etc.). `[documented]` https://www.researchgate.net/publication/4328314_Comparison_of_Method_Chunks_and_Method_Fragments_for_Situational_Method_Engineering , https://www.jucs.org/jucs_16_3/situational_method_engineering_state.html

**Selection/tailoring mechanism.** Three families: assembly-based (select chunks by matching situation to a *requirements map* of the project, then assemble by association/integration), extension-based (apply extension patterns to an existing method), paradigm-based (instantiate/abstract from a metamodel). Chunk selection uses *situational factors* / contingency factors (project size, novelty, risk, stakeholder dispersion…) and *similarity measures* between the project's intention map and chunk interfaces. `[documented]` Henderson-Sellers & Ralyté 2010 review (JUCS 16(3)); the 2014 Springer book (Henderson-Sellers, Ralyté, Ågerfalk, Rossi) https://link.springer.com/book/10.1007/978-3-642-41467-1 formalises this and adds *method rationale* (Ågerfalk & Wistrand): every fragment carries the goals/values that justify it, so a tailoring decision can be traced to a rationale rather than a preference. `[documented]` https://link.springer.com/chapter/10.1007/978-3-642-41467-1_3

**OPEN Process Framework (OPF).** Firesmith & Henderson-Sellers 2002: a metamodel with Work Units (Process, Task, Technique), Work Products, Producers; "producers perform work units, work units maintain work products"; a repository of reusable components; and explicit *construction / tailoring / extension guidelines* — the distinctive OPF idea being a **deontic matrix**: for each (task, technique) or (task, work product) pair a possibility value in {mandatory, recommended, optional, discouraged, forbidden}, set per organisation/project. `[documented]` https://link.springer.com/article/10.1023/A:1020570027891 , https://www.sei.cmu.edu/documents/153/2005_019_001_29337.pdf ; deontic values `[inferred]` from the OPF book as summarised in those sources.

**What worked.** The chunk interface `<situation, intention>` is a clean, decades-old formalisation of "required inputs → produced outcome" and is exactly the two halves an engine needs (match situation against existing artifacts; match intention against the stage's required outcomes). OPF's deontic matrix is the first explicit *weighting* of activities (mandatory→forbidden) as data rather than prose. Method rationale gives you an answer to "why is this activity in the DAG?" — essential for an agent orchestrator that must explain skips.

**What failed.** Steghöfer: never broadly adopted `[documented]`. Reasons `[inferred]`: assembly was research-grade (similarity metrics over goal maps, manual "requirements map" elicitation); no method base of quality; chunk granularity fights (fragments vs chunks debate consumed the field); and the selection step stayed with an expert "method engineer" — the very role most organisations don't have. Henderson-Sellers & Ralyté's own review lists "lack of tool support" and "lack of industrial validation" as open issues. `[documented]` JUCS 16(3).

**Steal this for redkiln.**
- Activity schema ⊇ chunk interface: `situation` (required input artifacts / states, plus *contingency predicates* on the work item's classification) and `intention` (produced artifact / state). The engine's core loop is Ralyté's assembly step with an *exact* matcher instead of a similarity metric.
- OPF deontic values as the per-stage weight enum: `mandatory | recommended | optional | discouraged | forbidden`, resolved per (stage × work-item-kind). "Forbidden" matters for agents (e.g., `release` activities forbidden on a spike).
- Carry `rationale:` on every activity and every override so `redkiln explain <item>` can print why each node is in/out of the DAG.

## 4. Software process tailoring literature and standards

**Pedreira, Piattini, Luaces, Brisaboa 2007 — "A systematic review of software process tailoring"** (ACM SIGSOFT SEN 32(3)). Surveys approaches to tailoring; positions them by *what is tailored* (activities, artifacts, roles), *tailoring criteria* (project/organisation factors) and *support* (tool, method). Finding: most approaches were manual, criteria were loosely defined, and few were validated. `[documented]` https://dl.acm.org/doi/10.1145/1241572.1241584

**Xu & Ramesh 2007 — "Software Process Tailoring: An Empirical Investigation"** (JMIS 24(2)): two case studies; develops a model of how tailoring resolves project *challenges*; identifies tailoring as knowledge-intensive, done by project managers using tacit experience; companion work (HICSS 2003/2005) builds a knowledge-base tool that stores tailoring decisions + rationale for reuse. `[documented]` https://dl.acm.org/doi/10.2753/MIS0742-1222240211 , https://www.researchgate.net/publication/224739206_A_tool_for_the_capture_and_use_of_process_knowledge_in_process_tailoring . Signal: tailoring is *retrieval of past decisions*, not derivation from first principles. `[inferred]`

**Martínez-Ruiz, Münch, García, Piattini 2012 — "Requirements and constructors for tailoring software processes: a SLR"** (SQJ 20:229–260, 1990–2009 literature): enumerates requirements for a *variability notation* in five categories (variation points/variants, dependencies/constraints, binding time, traceability, tool support); leads to vSPEM, whose variability constructs were empirically 127% more understandable than SPEM's. `[documented]` https://link.springer.com/article/10.1007/s11219-011-9147-6 , https://digital-library.theiet.org/doi/10.1049/iet-sen.2010.0020

**Kalus & Kuhrmann 2013 — "Criteria for software process tailoring: a systematic review"** (ICSSP 2013, pp.171–180): 49 tailoring criteria from the literature, grouped (team: size, distribution, experience; internal environment: criticality, safety, legal; external: customer involvement, contract type; objectives: cost, time, quality; etc.), related to 20 exemplary *tailoring actions* (drop/add activity, change artifact detail, change review rigor, …). Central conclusion: "the factors influencing the tailoring are well understood, however, the consequences of the criteria remain abstract and need to be interpreted on a project-per-project basis." `[documented]` https://dblp.org/rec/conf/ispw/KalusK13.html , https://www.researchgate.net/publication/256471312_Criteria_for_Software_Process_Tailoring_A_Systematic_Review . Follow-on: Kuhrmann's HELENA surveys (2017–2021) show practitioners build hybrids by plugging fine-grained practices into a base framework, with "limited guidance on how teams integrate" them — i.e., tailoring in practice is ad hoc composition. `[documented]` https://pure.qub.ac.uk/files/178889830/HELENA_ICSSP_paper.pdf , https://arxiv.org/pdf/2101.08016

**Hurtado Alegría & Bastarrica 2011/2014 — MDE-based process tailoring.** Organisational process (SPEM model) + project *context model* (attributes with enumerated values) → ATL transformation rules → project-specific SPEM process. Later work auto-generates the transformation from variability annotations. Validated in a mid-size Chilean company's RE process. `[documented]` https://dl.acm.org/doi/10.1145/1987875.1987885 , https://onlinelibrary.wiley.com/doi/10.1002/smr.1576 , https://ceur-ws.org/Vol-1503/09_pap_silvestre.pdf . This is the most direct academic precedent for **deterministic tailoring as a function of a typed context model**. `[inferred]`

**V-Modell XT (German federal standard).** Tailoring is rule-driven and tool-executed: determine *project type* (directly or by answering "determining project characteristics"), then *project type variant*, then process modules (Vorgehensbausteine — bundles of activities, products, roles) and execution strategies are selected; the Projektassistent generates documentation, product templates and an initial plan. Four modules are always mandatory (project management, QA, configuration management, problem/change management). `[documented]` https://www.microtool.de/wissen-online/wie-funktioniert-v-modell-xt-tailoring/ , https://download.gsb.bund.de/BundesCIO/V-Modell_XT_Bund/V-Modell%20XT%20Bund-2.0-HTML/18621155da80798a.html . Ternité/Kuhrmann formalised its variability operations as a software process line. `[documented]` https://dl.acm.org/doi/abs/10.1002/smr.1751 . This is the one large-scale, decades-running example of **deterministic, questionnaire-to-DAG tailoring in production** for software processes. `[inferred]`

**ISO/IEC/IEEE 12207:2017 Annex A (normative tailoring).** Requires: identify and record circumstances influencing tailoring (stability/variety of environments, commercial/performance influences, risks, project scope, life-cycle model); take due account of life-cycle structures; obtain input from affected parties; make tailoring decisions (delete, add, modify processes/outcomes) and record them with rationale; conformance can be claimed to the tailored process. `[documented]` https://www.en-standard.eu/bs-iso-iec-ieee-12207-2017-systems-and-software-engineering-software-life-cycle-processes/ (Annex A summary), https://managementsystems.world/standard/iso-iec-ieee-12207 . Takeaway: the *standard* insists every tailoring decision be recorded with rationale — a compliance argument for redkiln's `explain` output. `[inferred]`

**CMMI OPD SP 1.3 / IPM SP 1.1.** The organisation must establish tailoring criteria and guidelines: which assets are essential to any defined process, "options that can be exercised and criteria for selecting among options", procedures for documenting tailoring and for waivers; projects then "establish the defined process" by applying them. `[documented]` https://www.wibas.com/cmmi/opdsp-13-establish-tailoring-criteria-and-guidelines , https://www.wibas.com/cmmi/ipmsp-11-establish-the-defined-process . Pattern: a mandatory core + options + selection criteria + waiver path.

**Boehm & Turner 2003/2004 — "Balancing Agility and Discipline".** Five factors on a polar chart: Size (people), Criticality (loss from defects: comfort → many lives), Dynamism (% requirements change/month), Personnel (Cockburn levels), Culture (% thriving on chaos vs order). Plotted, a project near the centre suits agile, near the edge plan-driven; Chapter 5 gives a five-step *risk-based* method: rate the risks of agile and of plan-driven approaches, and architect the process to mitigate the dominant ones. Explicitly a rubric with numeric axes. `[documented]` https://ptgmedia.pearsoncmg.com/images/9780321186126/samplepages/0321186125.pdf , https://www.academia.edu/18859063/Balancing_Agility_and_Discipline_Evaluating_and_Integrating_Agile_and_Plan_Driven_Methods

**Steal this for redkiln.**
- A **fixed, small context vector** per work item (Boehm–Turner style, ~5–8 axes with banded values: kind, criticality band, blast radius, novelty/uncertainty, external-facing?, regulated?, size band, has-repro?) is what every successful deterministic scheme binds rules to (V-Modell XT project characteristics; Hurtado's context model; CMMI options). Do not bind rules to the 49 Kalus–Kuhrmann criteria directly — they are the *input* to a classification step, not to activity rules.
- Model tailoring actions as the finite set Kalus–Kuhrmann and 12207 use: `add | drop | reduce-rigor | increase-rigor | merge | substitute` — and record every action with rationale (12207 A.2, CMMI waivers).
- Mandatory core per stage (V-Modell XT's four always-on modules) prevents the "tailor everything away" failure.
- Keep a **decision memory** (Xu & Ramesh): when a human overrides the engine, store `(context vector, activity, override, rationale)` and surface it next time the same context recurs.

## 5. Configurable process models (BPM) and software process lines

**C-EPC / questionnaire-driven configuration (La Rosa, van der Aalst, Dumas, ter Hofstede 2007–2009).** Reference process models get *configurable nodes* (functions can be ON/OFF/OPT; connectors restrict branching); *configuration requirements/guidelines* constrain valid combinations. The questionnaire layer: domain *facts* grouped into *questions*, with **order dependencies** and **domain constraints** (propositional formulas over facts); a mapping from facts to configurable nodes; tooling (Quaestio) answers questions interactively and "incrementally prevents invalid configurations by restricting the space of allowed answers based on previous answers", detects circular dependencies and contradictory constraints; the configured model is then *individualised* (variable elements removed). Applied to film post-production. `[documented]` https://kodu.ut.ee/~dumas/pubs/SoSymVariability.pdf , https://link.springer.com/article/10.1007/s10270-008-0090-3 , https://link.springer.com/chapter/10.1007/978-3-540-78238-4_43 . Later work extends to configurable BPMN and automated correctness-preserving configuration. `[documented]` https://link.springer.com/chapter/10.1007/978-3-319-15895-2_10

**Provop (Hallerbach, Bauer, Reichert 2008–2010).** A *base process* + *options* (INSERT/DELETE/MOVE/MODIFY adaptations at *adjustment points*) + a *context model* (variables with value ranges) + *context rules* that select options ("activity Maintenance must be performed if the required security level is high") + *constraints* between options (mutual exclusion, implication, hierarchy). Variants are configured by evaluating context rules; correctness of the resulting variant is ensured by construction/verification. `[documented]` https://www.uni-ulm.de/fileadmin/website_uni_ulm/iui/Ulmer_Informatik_Berichte/2009/UIB_2009-03.pdf , https://www.researchgate.net/publication/313838056_Capturing_variability_in_business_process_models_The_Provop_approach , https://link.springer.com/chapter/10.1007/978-3-642-00416-2_11

**Software process lines (Rombach 2005; Martínez-Ruiz et al.; Armbrust et al.).** Rombach argued for applying product-line thinking to processes: a reference process with commonality/variability, variants derived by extension/modification ("descending") or abstracted from existing variants ("ascending"). vSPEM adds variation points/variants to SPEM; SMartySPEM uses UML-profile stereotypes; CVL and feature models have been tried; Armbrust et al. (Fraunhofer IESE, "Scoping software process lines") mine commonality from existing project processes. SLRs (2014) report many notations, few industrial validations, and that *annotative* (mark variability in one model) approaches are more understandable than *compositional* ones for process lines. `[documented]` https://link.springer.com/chapter/10.1007/978-3-319-13036-1_11 , https://digital-library.theiet.org/doi/10.1049/iet-sen.2010.0020 , https://link.springer.com/chapter/10.1007/978-3-642-39259-7_14 , https://www.researchgate.net/publication/260779562_SMartySPEM_A_SPEM-Based_Approach_for_Variability_Management_in_Software_Process_Lines

**What worked.** BPM configuration has the strongest *deterministic* results in this whole survey: facts → constraints → configuration is decidable, checkable for contradictions, and supports incremental narrowing; Provop's context rules are the closest published analogue to "activity carries its own applicability rule". Process lines gave a vocabulary (variation point, variant, binding time, constraint) and the insight that annotating a single base model beats composing fragments for understandability.

**What failed.** `[inferred]` Both BPM configuration and process lines assume a *stable reference model* and *upfront* configuration at design time; they don't natively handle "artifacts that already exist" (runtime state) — configuration is static, enactment is separate. Software process lines never got a widely used tool (vSPEM/SMartySPEM stayed academic). The questionnaire approach also requires a human to answer facts — fine for redkiln if facts are computed from the work item and repo.

**Steal this for redkiln.**
- Make the catalog a **base process + annotated variation points** (annotative, not compositional): each activity in a stage is a configurable node with a *presence condition* (a propositional formula over the context vector and artifact-existence facts). This is C-EPC ON/OFF/OPT + Provop context rules, in one schema.
- Add **constraints between activities** (requires / excludes / ordering) as a separate, checkable layer, and run La Rosa's checks at catalog load: contradictory constraints, circular dependencies, unreachable nodes. A SAT/propositional check over a few hundred booleans is trivial in Rust.
- Treat *facts* as computed, not asked: `has_artifact(competitor_analysis)`, `kind == bug`, `criticality >= high`. The questionnaire becomes a fact-derivation function over the item + repo; a human can override individual facts (with rationale) but never edits the DAG directly.
- Report the *individualised* DAG (variable elements removed) plus the list of dropped activities and the fact/rule that dropped each one.

## 6. 2023–2026: LLM agents + software process models / method engineering

- **MetaGPT (ICLR 2024)** encodes SOPs as role-specific prompt sequences with structured intermediate artifacts (PRD → design → tasks → code); "assembly line" role assignment; the process is *fixed in code*. `[documented]` https://arxiv.org/abs/2308.00352 . **ChatDev** simulates a chat-based software company through fixed phases (design → coding → testing → documentation) with role pairs. `[documented]` https://arxiv.org/pdf/2604.26275 (survey). Both are evidence that a *static* SOP with typed artifacts improves output over free-form agents — but neither tailors the SOP to the task.
- **Think-on-Process (Lin, Zhou, Chen, Qian 2024)**: criticises that frameworks "rigidly fix the software development process… in code form"; mines process models from past instances (process mining over successful runs) and prompts the LLM to *generate* a per-task process. `[documented]` https://arxiv.org/abs/2409.06568 . This is the LLM-driven alternative to redkiln's deterministic engine; its own motivation (variability across tasks) is redkiln's motivation, but its mechanism moves the tailoring decision into the model. `[inferred]`
- **"Evaluating Classical Software Process Models as Coordination Mechanisms for LLM-Based Software Generation" (2025)** and **"Evaluating Software Process Models for Multi-Agent Class-Level Code Generation" (2025)**: 132 runs across Waterfall/V-Model/Agile × 4 GPT variants; process choice significantly affects cost and quality (Waterfall cheapest, Agile highest quality, V-Model most verbose); "process selection should reflect project goals." `[documented]` https://arxiv.org/html/2509.13942 , https://arxiv.org/html/2511.09794 . Empirical support that *which activities run* is a first-order lever for agent output — i.e., the tailoring engine is not ceremony.
- **"Specifying AI-SDLC Processes: A Protocol Language for Human-Agent Boundaries" (Prifti, Birkbeck, June 2026)**: a DSL (YAML protocols) with formal abstract syntax, well-formedness conditions (WF1–WF5), operational semantics and enforcement invariants (INV1–INV4); separates *policy* (declared intent) from *mechanism* (structural enforcement — validation tokens as preconditions for dispatch, capability boundaries at the MCP layer). Key claim: structural enforcement "eliminates *process* non-determinism (agents skipping, drifting from, or reinterpreting protocol steps)" while only *bounding* agent non-determinism; failure rate bounded by a weighted product of agent and validator rates; 2+N team pattern (two human-in-control roles + N agents). Notes that competing approaches "encode process in agent prompts (subject to drift)". `[documented]` https://arxiv.org/html/2606.20615v2
- **"Agentic AI in the SDLC" (Bhati, Apr 2026)** proposes a six-layer reference architecture and an A-SDLC contrasted with the classical SDLC; consolidates SWE-bench Verified progress 1.96% → 78.4% (Oct 2023 → Apr 2026). `[documented]` https://arxiv.org/abs/2604.26275
- **"Using LLMs and Essence to Support Software Practice Adoption" (Aug 2025)**: RAG chatbot over the Essence kernel/practices; LLM used to *explain and assess* Essence, not to select activities. `[documented]` https://arxiv.org/abs/2508.16445 . Confirms Essence is the process vocabulary the LLM-era literature reaches for, and that nobody has yet wired Essence criteria to an agent orchestrator's scheduler. `[inferred]`
- **"Evaluation-Driven Development of LLM Agents: A Process Model and Reference Architecture" (2024/25)** — process model for building agents; adjacent, not about tailoring. `[documented]` https://arxiv.org/html/2411.13768v2
- **TOSEM 2025 survey "LLM-Based Multi-Agent Systems for SE"** notes most systems "rely on predefined roles and fixed workflows". `[documented]` https://arxiv.org/html/2404.04834v4

**Steal this for redkiln.**
- Prifti's policy/mechanism split is the strongest 2026 argument for the design question: put *applicability* (policy) in declarative activity rules, and make the *engine* the mechanism so an agent cannot skip a mandatory activity — the DAG is built outside the model and enforced by dispatch preconditions (validation tokens ≈ redkiln's stage-gate verdicts).
- Keep typed intermediate artifacts (MetaGPT's lesson) as the *facts* the engine reads.
- Reserve ToP-style LLM process generation for the *catalog authoring* loop (mining which activities correlated with success), never for per-item DAG construction.

## Direct answers

### (a) Is there precedent for activity-level self-describing applicability rules rolled into a per-stage rubric?

Yes — four independent lineages, and they converge on the same schema:
1. **Essence** (OMG standard, 2014–2018): every Activity/Activity Space declares `Input`, `Entry Criteria`, `Completion Criteria` as `Alpha::State` / work-product level-of-detail; the spec's stated purpose is a method that "will return advice on what to do next", and Level-3 conformance exists precisely so tools can do "task generation… and completeness checking". `[documented]` This is activity-level self-description; the "per-stage rubric" is the stage's required Alpha-state vector.
2. **SME method chunks** (Ralyté/Rolland; Henderson-Sellers et al. 2014): interface = `<situation (precondition), intention (postcondition)>` + descriptor with reuse context; OPF adds the deontic matrix (mandatory…forbidden) as the weight. `[documented]`
3. **Provop / C-EPC**: activities as configurable nodes with presence conditions over a context model, plus inter-node constraints, plus decidable configuration. `[documented]`
4. **V-Modell XT / Hurtado MDE tailoring**: rules from a typed project characterisation to a selected set of process modules, executed by a tool. `[documented]`
What is *not* precedented: combining these with **runtime artifact state** ("already has a competitor analysis") so the DAG is rebuilt per work item and re-evaluated as artifacts appear — Essence's non-monotonic state reassessment is the only piece of the literature that even conceptualises this, and its checklists are human-evaluated. Redkiln's contribution would be machine-decidable evidence predicates + per-item recomputation. `[inferred]`

### (b) What does the literature say about determinism of tailoring — rules vs expert judgement?

- The criteria side is settled and enumerable (Kalus & Kuhrmann's 49; Boehm–Turner's 5; 12207 Annex A's circumstance list; CMMI's options). The *consequence* side is where the literature explicitly stops: "the consequences of the criteria remain abstract and need to be interpreted on a project-per-project basis" `[documented]` (Kalus & Kuhrmann 2013); Xu & Ramesh show tailoring in practice is tacit, experience-driven, and best supported by *reusing past decisions* `[documented]`; HELENA shows practitioners compose hybrids ad hoc `[documented]`.
- Where determinism was achieved it was by **narrowing the problem**: a fixed context vector with banded values (V-Modell XT project type/characteristics; Hurtado's context model), a finite set of tailoring operations (add/drop/modify; Provop's four adaptations), propositional constraints checked for consistency (La Rosa), and a mandatory core that cannot be tailored away (V-Modell XT, CMMI "essential assets"). Within those bounds, tailoring is a pure function and the BPM community proved it can be verified for correctness by construction. `[documented + inferred]`
- The 2026 AI-SDLC protocol paper reframes the question usefully: determinism you need is *process* determinism (steps cannot be skipped or reinterpreted), achieved by structural enforcement outside the model; *agent* non-determinism inside an activity is bounded, not eliminated. `[documented]` That maps directly to "engine builds the DAG deterministically; the LLM only executes nodes".
- Net: the literature does **not** support "an expert's judgement can be fully replaced by rules across all 49 criteria". It **does** support "rules over a small typed context + artifact facts, with a recorded waiver/override path (CMMI waivers, 12207 rationale, Xu–Ramesh decision memory) for the residue". Design the engine as deterministic-by-default with an explicit, logged escape hatch, not as a complete theory of tailoring. `[inferred]`

### (c) Known failure modes

1. **Method bloat / over-ceremony.** RUP → OpenUP existed because RUP's full library was unusable without heavy tailoring; Boehm–Turner's whole book is about the cost of misplaced discipline; Essence's founding motivation was to strip processes to a kernel. Tailoring frameworks that default to "everything on, then prune" produce bloat; those that default to "mandatory core + evidence-driven additions" (V-Modell XT, Essence "start with a minimal method adding practices as the endeavor progresses" `[documented]` spec §8.1.1) don't. Redkiln should default activities to `optional` and require positive evidence/conditions to promote them.
2. **Authoring cost exceeds consumption value.** SPEM/EPF and Essence Level-3 practices need specialist tooling and modelling skill; content rotted (EPF's published Scrum/XP/OpenUP "outdated" `[documented]`); students and practitioners could not instantiate activity spaces `[documented]`. Mitigation: a tiny YAML/TOML schema, linted, with the engine as the only consumer, and catalog validation in CI.
3. **Documentation, not execution.** EPF produced HTML method sites; nothing in the loop *consumed* the model, so there was no forcing function to keep it correct; IBM left for DOORS Next (traceability-integrated) `[documented]`. Mitigation: the engine must fail loudly on a malformed catalog and the DAG must gate dispatch.
4. **One-to-one variability / clone-and-own.** EPF's variability limitation forced copy-paste clones `[documented]`; process-line SLRs found compositional variability less understandable than annotative `[documented]`. Mitigation: single base catalog with presence conditions and a small overlay algebra (contributes/replaces/extends), not per-tenant forks.
5. **Static configuration divorced from runtime state.** C-EPC/Provop/V-Modell XT configure once at project start; they can't answer "we already have X" mid-flight. `[inferred]` Mitigation: recompute the DAG on every artifact change; allow states to regress (Essence).
6. **Expert-in-the-loop bottleneck.** SME's "method engineer" role and CMMI's SEPG rarely exist in small orgs; tailoring degenerates to ad hoc (HELENA). `[documented + inferred]` Mitigation: engine + decision memory replaces the role for the common case.
7. **Human-judged checklists masquerading as predicates.** Essence checklist items like "Stakeholders: In Agreement" look like preconditions but are not machine-decidable; an engine that treats them as booleans will either block forever or rubber-stamp. `[inferred]` Mitigation: every criterion must name an evidence artifact or verdict record; judgement-only criteria are routed to a human gate node, not a boolean.
8. **Prompt-encoded process drift** (2026): processes living in agent prompts are "subject to drift" and skipping `[documented]` — the exact failure redkiln's deterministic engine is meant to prevent; the literature's recommended fix (structural enforcement, validation tokens as dispatch preconditions) is the same as redkiln's stage-gate design.

## Proposed minimal activity schema distilled from the above (for the design note)

```yaml
id: discovery.competitor_analysis
stage: discovery                      # SPEM: process descriptor context
kinds: [initiative, project]          # V-Modell XT: project type binding
inputs:                               # SME situation / Essence Input
  - artifact: initiative.charter      # must exist (fact)
produces:                             # SME intention / Essence Completion Criteria
  - artifact: discovery.competitor_analysis
  - state: Opportunity::ValueEstablished   # Essence alpha-state progressed
presence:                             # Provop context rule / C-EPC ON|OFF|OPT
  when: "kind in [initiative, project] and external_facing"
  weight: recommended                 # OPF deontic: mandatory|recommended|optional|discouraged|forbidden
  skip_if: "exists(artifact: discovery.competitor_analysis, fresher_than: charter)"
requires: []                          # inter-activity constraints (La Rosa)
excludes: []
rationale: "External-facing work needs a positioning baseline before specification."
```

Engine contract `[inferred]`: `facts = derive(item, repo)` → evaluate every `presence.when` and `skip_if` → include `mandatory` unconditionally → order by `inputs`/`produces` (topological) and `requires` → check `excludes`, unreachable stage-exit states, cycles → emit DAG + per-node rationale + list of dropped nodes with the rule that dropped them → any human override is recorded `(facts, activity, decision, rationale)` and replayed on identical facts (Xu & Ramesh / CMMI waiver).
