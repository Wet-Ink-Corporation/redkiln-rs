# Archon and Shipmates — granular product research (2026-09-03)

## 1. Archon (coleam00/Archon)

### Current status
Archon underwent a **complete rewrite on 2026-04-07**: the original Python task-management + RAG tool was archived (preserved on branch `archive/v1-task-management-rag`, nothing deleted) and replaced by an entirely different product — a TypeScript **workflow engine for AI coding agents** ("the first open-source harness builder for AI coding") ([Issue #957](https://github.com/coleam00/Archon/issues/957)). The maintainer states explicitly: "this is an entirely different product... There is no migration path between them."

- **Stars**: ~22.4k–23.3k (observed climbing across this session, e.g. 22.4k → 22.8k → 23.3k within days), 3.5k forks, 227 watchers ([repo](https://github.com/coleam00/Archon)).
- **Maintainer**: Cole Medin (`coleam00`), with a significant co-maintainer `Wirasm` who authors most recent releases.
- **License**: MIT ([LICENSE](https://github.com/coleam00/Archon/blob/dev/LICENSE)).
- **Commercial model**: Fully open source / self-hosted; no paid tier found. Anonymized telemetry (PostHog) is on by default but opt-outable via `ARCHON_TELEMETRY_DISABLED`/`DO_NOT_TRACK`/`POSTHOG_API_KEY=off`; collects only categorical usage (workflow names for bundled workflows, node types/features used, success/failure, duration, cost totals) — explicitly never code, prompts, or error text ([README Telemetry section](https://github.com/coleam00/Archon)).
- **Release cadence**: Active, frequent point releases (v0.3.3 → v0.4.1 across roughly six weeks, Apr 10–May 28 2026), each with detailed changelogs ([Releases](https://github.com/coleam00/Archon/releases)).

### Architecture
- **Language/runtime**: Bun + TypeScript (workflow engine core); SQLite (default) or PostgreSQL (14 core tables: Codebases, Conversations, Sessions, Workflow Runs, Isolation Environments, Messages, Workflow Events, Users, User Identities, Workflow Node Sessions, Codebase Env Vars, User GitHub Tokens, User Provider Keys, User AI Prefs; plus Better Auth tables on Postgres) ([README architecture diagram](https://github.com/coleam00/Archon)).
- **Components**: Platform Adapters (Web UI, CLI, Telegram, Slack, Discord, GitHub webhooks) → Orchestrator (message routing/context) → Command Handler (slash commands) + Workflow Executor (YAML DAG) + AI Assistant Clients (Claude, Codex, Gemini/Pi, OpenCode, GitHub Copilot as a "community provider").
- **Persistence**: DB-backed (SQLite/Postgres), not files-in-repo for state — but workflow *definitions* are YAML files committed to the target repo under `.archon/workflows/<pack>/<workflow>/` (or `~/.archon/workflows/` for user-global ones), so process-as-code lives in git while execution state lives in the DB.
- **Work-item modeling**: No initiative/project/story hierarchy — the unit of work is a **workflow run** (a DAG of typed nodes: `prompt`/AI nodes, `bash`/deterministic nodes, `loop` nodes with `until:` conditions, `approval`/interactive gates, `script:` nodes for inline TS/Python). No backlog or ticket hierarchy is modeled; GitHub Issues/PRs are the closest thing to backlog items, consumed via the `archon-fix-github-issue` workflow.
- **Workflow definition**: YAML, e.g. `.archon/workflows/build-feature.yaml`, with `nodes:`, `depends_on:`, `prompt:`, `bash:`, `loop: {until: ..., fresh_context: true}`, `interactive: true` for human gates. Ships 17–19 default workflows (e.g. `archon-idea-to-pr`, `archon-piv-loop`, `archon-comprehensive-pr-review`, `archon-resolve-conflicts`) ("What Can You Automate?" table, [README](https://github.com/coleam00/Archon)).
- **Harness support**: Claude Code, OpenAI Codex, Google Gemini/Pi are first-class; OpenCode and GitHub Copilot are "community providers" (`builtIn: false`) added in v0.4.0 ([v0.4.0 changelog](https://github.com/coleam00/Archon/releases)). MCP support exists for Codex nodes and more broadly (`mcp:` on nodes).
- **Dispatch**: Headless CLI invocation of the underlying coding tool inside an isolated **git worktree per run** (not Docker containers) — "every workflow run gets its own worktree. Run 5 fixes in parallel." Binary distribution requires `CLAUDE_BIN_PATH` since compiled Archon binaries don't bundle Claude Code.

### Human-in-the-loop
- Explicit **approval/loop nodes** (`interactive: true`, `until: APPROVED`) pause a run and wait for human input from whichever platform kicked it off (CLI, Web, Slack, Telegram, Discord). A `workflow_approval_resolved` telemetry event records only the binary approve/reject decision, never comments.
- `archon workflow approve/resume/reject` CLI commands manage gate resolution; a bug fixed in v0.4.0 made resume work from Slack/Telegram, not just web ([v0.4.0 changelog](https://github.com/coleam00/Archon/releases)).

### UI
Web dashboard ("Mission Control") with: **Chat** (streaming conversation + tool-call visualization), **Dashboard** (filterable run history by project/status/date), **Workflow Builder** (visual drag-and-drop DAG editor with loop-node support, added/fixed in v0.4.0), **Workflow Execution** (step-by-step progress view). An experimental run-centric `/console` UI was added in v0.4.0 as an isolated, lint-guarded spike. The sidebar aggregates conversations from *all* platforms (CLI, Slack, Telegram, GitHub issue interactions) into one place ([README Web UI section](https://github.com/coleam00/Archon)).

### GitHub integration
Deep: GitHub Webhooks adapter (15 min setup), GitHub App authentication added in v0.4.0 (replacing shared PAT with per-installation token minting, never persisted, via a `git-credential-archon` helper), `archon-fix-github-issue` / `archon-create-issue` / `archon-issue-review-full` workflows, PR creation and multi-agent PR review (5 parallel reviewers) built in ([v0.4.0 changelog](https://github.com/coleam00/Archon/releases)).

### Knowledge management
The **old** Python Archon (v1, archived) was explicitly a RAG/knowledge-base tool ("knowledge and task management backbone," per the [public-space/Archon-OS fork](https://github.com/public-space/Archon-OS) description of the pre-rewrite architecture). The **current** TypeScript Archon has **no RAG/knowledge-base subsystem** — it dropped that scope entirely in favor of deterministic workflow orchestration. Teams wanting the old knowledge/task-management behavior must use the archived v1 branch, which is not actively maintained going forward.

### Docs approach
Dedicated docs site at [archon.diy/docs](https://archon.diy/docs/), including a 10-chapter narrative tutorial ("The Book of Archon"), CLI reference, "Authoring Workflows"/"Authoring Commands" guides, configuration reference, AI-assistants setup guide, deployment guide, architecture reference, and troubleshooting page. Also ships `llms.txt`, `llms-full.txt`, `llms-small.txt` at the docs root specifically for LLM consumption ([README Documentation table](https://github.com/coleam00/Archon)).

### Community sentiment
- The **rewrite was polarizing by nature** — old users of the Python task-management/RAG tool lost that product entirely with no migration path; issue #957 exists specifically to explain "What happened to the old Archon?" implying enough user confusion/concern to warrant a pinned explainer. Related issues like [#952](https://github.com/coleam00/Archon/issues/952) ("Open source Archon: migrate new codebase to coleam00/Archon") and [#901](https://github.com/coleam00/Archon/issues/901) ("Task management") reflect users specifically asking about the lost task-management capability. UNVERIFIED: exact tone/volume of complaints in those threads was not read in full detail due to scope; the issue titles alone confirm this was a live pain point.
- Despite the disruption, star growth has been strong and continuous (trending on Trendshift, [trendshift.io/repositories/13964](https://trendshift.io/repositories/13964)), suggesting the new product found fast traction independent of the old user base.
- Positive signal: release notes show steady community PR contributions (community providers for OpenCode and GitHub Copilot were contributed, not maintainer-authored), and releases collect thumbs-up/rocket reactions from multiple distinct users each time.
- x64 hardware constraint (binary install requires AVX2) and the `CLAUDE_BIN_PATH` requirement for compiled binaries are known friction points called out directly in the README's install instructions, implying they were common support questions.

### Best parts worth stealing
1. **Deterministic YAML DAG workflows with mixed AI/bash/script nodes** — the "Dockerfile for AI coding" framing is a strong, legible mental model: gates, loops, and validations are code, not vibes.
2. **Per-run git worktree isolation** baked into the orchestration model, enabling safe parallelism by construction.
3. **Explicit `interactive`/`until: APPROVED` loop-gate primitive** as a first-class node type — a clean, reusable pattern for human approval gates rather than a bolted-on review step.
4. **Multi-platform adapter model** (CLI/Web/Slack/Telegram/Discord/GitHub) unified behind one orchestrator and one run history — "kick off anywhere, see it in one dashboard."
5. **Privacy-respecting, granular, opt-outable telemetry** as a documented default — a good transparency template.

### Things to avoid
1. **Breaking rebrand-in-place**: reusing the same repo/name for a totally different product with no migration path caused real confusion — a cautionary tale for redkiln-rs if its scope ever pivots.
2. **Dropped knowledge-base/RAG scope entirely** in the rewrite — an explicit reminder that "orchestration" and "knowledge base" are easy to decouple accidentally; redkiln-rs should keep its KB-in-repo commitment deliberate and not let it erode under later refactors.
3. **No backlog/work-item hierarchy** — Archon's unit of work is a bare workflow run tied loosely to GitHub issues; it has no initiative→project→story structure, so it can't answer "what's our sprint status" — a gap redkiln-rs's structured backlog directly addresses, but worth knowing Archon nearly ignores this space entirely.
4. **Compiled-binary/runtime coupling friction** (AVX2 requirement, `CLAUDE_BIN_PATH` indirection) — avoidable packaging pain.

## 2. Shipmates (KranzL/shipmates-oss)

### Identity confirmation
The canonical repo is **[github.com/KranzL/shipmates-oss](https://github.com/KranzL/shipmates-oss)**, linked directly from the product site **[shipmates.vc](https://shipmates.vc)** ("Source" link and "Get Started on GitHub" CTA both point there). Built by **Luke Kranz** (`luke@kranz.com`, [LinkedIn: Senior Staff AI Engineer @ Fanatics](https://www.linkedin.com/in/luke-kranz-ucf/)). Tagline: "Talk to your AI dev team through Discord voice calls. Start a call, give your agents work, and disconnect. They keep coding."

**Note on the "referee" claim**: extensive searching (GitHub commit search API, issue search API, the repo's own README/file tree, web search, and searches of the author's public X account) turned up **no evidence of a "referee" component ever existing in shipmates-oss** — the repo has only 3 commits total and no issues/PRs history to search. This detail is **UNVERIFIED**; it may refer to a different/earlier iteration not reflected in the current 3-commit history, a private pre-OSS-release version, or a conflation with a similarly-themed project (e.g. `KranzL/jje`, a separate "generator-critic harness for Claude Code: Planner/Executor/parallel panel of tool-backed jurors/a routing Judge" by the same author, which has judge/juror concepts but is a distinct repo). Could not confirm or find the deletion event.

### Current status
- **Extremely early-stage**: only **3 commits**, **1 star**, **0 forks**, **0 watchers** as of this research date ([repo page](https://github.com/KranzL/shipmates-oss)). No releases/tags visible, no CI badges, no visible issues/PR activity.
- **License**: Apache-2.0.
- **Maintainer**: solo (Luke Kranz).
- **Commercial model**: dual — free/open-source self-hosted version (`shipmates-oss`, Apache-2.0) alongside what shipmates.vc implies is (or will be) a hosted/managed offering; the marketing site emphasizes "Open Source / Self-Hosted" as the primary CTA with no separate pricing page found. UNVERIFIED whether a paid hosted tier currently exists — the site only shows the OSS GitHub link.

### Architecture
- **Language**: Go (each service is "a standalone go module": `bot`, `stream-relay`, `webhook-router`, `pr-review`, `ci-diagnosis`, `test-gen`).
- **Components** (Docker Compose services, per [README](https://raw.githubusercontent.com/KranzL/shipmates-oss/main/README.md)):
  - `db` (Postgres 16) — stores agents, sessions, config, everything.
  - `bot` — the main brain: Discord/Slack bot, voice pipeline, orchestrator, task delegation.
  - `stream-relay` — WebSocket relay streaming live terminal output from agent containers.
  - `docker-proxy` — proxies the Docker socket so `bot` can safely spin up coding containers.
  - `webhook-router` — receives GitHub webhooks, routes to `pr-review` or `ci-diagnosis`.
  - `pr-review` — reviews PRs using the configured LLM.
  - `ci-diagnosis` — diagnoses CI failures, suggests fixes.
  - `test-gen` — coverage-guided test generation.
- **Persistence**: Postgres (DB-backed), not files-in-repo. No workflow-as-code / YAML definition layer exists — behavior is hardcoded in the Go services, configured via `shipmates.config.yml`.
- **Work-item modeling**: **None** — no initiative/project/story hierarchy, no backlog concept at all. The unit of interaction is a voice/text instruction routed to a named agent ("alex, review the auth module"); there's no persistent task/ticket state model beyond "agents, sessions, config."
- **Workflow definition**: No declarative workflow language; agent behavior/routing is defined by static config (`shipmates.config.yml`) naming agents, personalities, voices, and scoped repo/directory/language access — not a pipeline DSL.
- **Harness support**: Claude Code, OpenAI Codex CLI, Google Gemini CLI as "container providers" that actually write code; Venice AI, Groq, Together AI, Fireworks AI, and any OpenAI-compatible custom endpoint as "chat-only" providers (review/Q&A only, no code-writing).
- **Dispatch**: Headless CLI dispatch inside **isolated Docker containers** (not git worktrees) — each container clones the target repo, runs the coding CLI, and pushes a branch. A `docker-proxy` service mediates access to the Docker socket for safety.

### Human-in-the-loop
Async, chat-native: "When agents get stuck, they message you on Discord or Slack. Answer when you can. They pick back up automatically. No babysitting required." This is a **reactive clarification model**, not a structured approval-gate model — there is no described stage-gate or explicit approve/reject mechanism comparable to Archon's `interactive`/`until: APPROVED` nodes; human input appears to be free-text Q&A resumption rather than a formal review checkpoint.

### UI
**No web dashboard** — Shipmates is chat-first by design (Discord voice/text, Slack). The `stream-relay` service streams live terminal output, implying some UI exists to view it, but no browser-based kanban/dashboard is described in the README or site. Voice-first UX is the differentiator: distinct agent voices via ElevenLabs (paid) or local Piper TTS (free) "so you can tell who's talking without looking at a screen."

### GitHub integration
Solid: `webhook-router` service ingests GitHub webhooks and routes to automated `pr-review` (LLM-based PR review) and `ci-diagnosis` (CI failure diagnosis) services; agents push branches and (implied) open PRs directly. No explicit GitHub Issues/Projects sync beyond `GITHUB_TOKEN`-based repo access.

### Knowledge management
**None found** — no RAG, no docs ingestion, no knowledge-base concept anywhere in the README, site, or repo file tree. This is a pure task-dispatch/execution tool, not a knowledge system.

### Docs approach
Minimal — a single README with a docker-compose service table, provider table, quick-start, and env-var list. No dedicated docs site, no docs.diy-style microsite, no llms.txt. Setup is via an interactive `setup.sh` wizard.

### Community sentiment
Given only 1 GitHub star and 3 commits, there is **effectively no independent community discussion yet** — no Reddit threads, HN posts, or GitHub issues were found despite targeted searches across r/ClaudeAI-style terms, "shipmates github," and X. This appears to be a very recently launched, solo-founder side project rather than an established tool with a track record. **Mark as UNVERIFIED / insufficient public data**: no user complaints, praise, or abandonment signals could be found because the project does not yet appear to have a real external user base to generate them.

### Best parts worth stealing
1. **Voice-first, async task dispatch** — "join a call, describe the task, hang up" is a genuinely novel UX angle on reducing the time-to-start friction (their stated "time value of momentum" thesis) that redkiln-rs's chat/CLI-only model doesn't address, though it may be out of scope for redkiln-rs's headless-dispatch design.
2. **Named agents with scoped repo/directory/language access** ("frontend agent only touches the UI, backend agent stays in the API layer") — a lightweight, human-legible permission model worth considering for multi-harness dispatch boundaries.
3. **Docker-container-per-task isolation with a dedicated docker-proxy for socket safety** — a concrete, security-conscious pattern for headless dispatch that's more locked-down than raw docker socket mounting.
4. **Built-in `ci-diagnosis` and `test-gen` as dedicated microservices** — treating CI-failure diagnosis and coverage-guided test generation as first-class, separately deployable capabilities rather than ad hoc prompts.
5. **Async "agent gets stuck → pings you on chat → resumes automatically"** — a low-ceremony human-in-the-loop pattern that's cheap to implement, useful as a fallback alongside redkiln-rs's formal stage gates.

### Things to avoid
1. **No workflow-as-code / no work-item hierarchy** — Shipmates has zero backlog modeling; it's purely reactive task dispatch with no auditable process definition, the opposite of redkiln-rs's initiative→project→story + stage-gate design. Confirms that voice/chat-dispatch tools alone don't solve SDLC process rigor.
2. **No structured approval gates** — "message you when stuck, resume when you reply" is not equivalent to an enforced human-approval stage gate; it's ad hoc, not auditable, and doesn't block progression on rejection in any described way.
3. **Extremely early/unproven codebase** (3 commits, 1 star, solo maintainer, no docs site, no CI badge, no releases) — treat any specific architectural claims here as a snapshot of a nascent project, not a battle-tested reference implementation.
4. **The "referee" feature this brief expected could not be verified** — a caution against taking secondhand claims about specific named features at face value without a primary source; document such claims as unverified rather than propagating them.
