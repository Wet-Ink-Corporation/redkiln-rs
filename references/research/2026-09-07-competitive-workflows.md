# Competitive survey: how others make different work-item types run different stages/activities

Date: 2026-09-07. Scope: classic trackers/process templates (A) and 2025–2026 AI SDLC frameworks (B), each extracted on six axes (C): (1) work-item taxonomy, (2) stage model, (3) activity catalog + size, (4) selection mechanism (who decides what runs), (5) pre-existing artifacts / re-entry, (6) complaints. Tags: **[documented]** = read from primary/secondary source at the URL; **[inferred]** = my reading, not stated by the vendor. Companion to `2026-09-03-workflow-model.md` (process canon + engine contract); this note is about *competitors*, not standards.

Redkiln frame for comparison: item kinds initiative / project / story / bug / incident / spike; classification = GitHub Issue **type + labels**, hierarchy = **sub-issues**; a **deterministic engine** picks stages/activities per item. The question everywhere below is: *where does "what runs for this kind of item" live, and who owns that decision?*

---

## A. Classic trackers and process templates

### A1. Jira (Software + JSM + Product Discovery)

1. **Taxonomy** [documented]: hierarchical issue types (Epic > standard types Story/Task/Bug > Sub-task), grouped per project by an **issue type scheme**. JSM adds request types on top of issue types (Incident, Problem, Change, Service request, Post-incident review). JPD adds **Idea** as an issue type with delivery links to any Software issue type — one idea → many epics across projects ([JPD ideas](https://www.atlassian.com/software/jira/product-discovery/guides/ideas/overview), [delivery tickets](https://www.atlassian.com/software/jira/product-discovery/guides/delivery/overview)).
2. **Stage model** [documented]: a **workflow** = statuses + transitions; a **workflow scheme** maps *each issue type to exactly one workflow*; per-type divergence is therefore a property of the project scheme, not the item ([manage workflows and schemes](https://support.atlassian.com/jira-cloud-administration/docs/create-and-manage-issue-workflows-and-issue-workflow-schemes/)). This is the canonical "workflow per issue type" design and the direct ancestor of redkiln's per-kind stage list.
3. **Activity catalog**: none as such. The unit is the **transition**, decorated with **conditions** (may this user fire it?), **validators** (is input valid?), **post-functions** (side effects: set field, fire event, create sub-task); execution order conditions → validators → post-functions ([advanced workflows](https://support.atlassian.com/jira-cloud-administration/docs/configure-advanced-issue-workflows/), [workflow condition module](https://developer.atlassian.com/cloud/jira/platform/modules/workflow-condition/)). Automation rules (trigger → conditions → actions) are the de-facto activity layer, with a few hundred action types incl. "assign Rovo agent". Rovo agents can be triggered by workflow transition, automation, or assignment as an assignee ([Rovo automation](https://community.atlassian.com/forums/Rovo-questions/Automating-a-rovo-agent-as-the-assignee/qaq-p/3280944)).
4. **Selection**: **admin-designed, static.** Type → workflow is a lookup table; within a workflow, *the human* chooses the transition; conditions/validators gate but never choose. Per-type branching *inside* one shared workflow is a common anti-pattern solved by validators keyed on issue type ([community thread](https://community.atlassian.com/t5/Jira-Core-Server-questions/Workflow-validator-for-specific-issue-type/qaq-p/1342468)).
5. **Re-entry / pre-existing artifacts**: statuses are re-enterable via loop transitions; no notion of "artifact already exists, skip stage". JPD → delivery is a *link*, not a promotion: the idea keeps its own lifecycle while epics run theirs [documented].
6. **Complaints** [documented]: scheme sprawl ("the sprawl trap" — one workflow per type per project multiplies configuration; [resumelens](https://www.resumelens.org/blog/jira/jira-workflows-and-schemes)); validators/post-functions are invisible to users so transitions "mysteriously" fail; ceremony grows with schemes. Lesson: **per-type workflows must be derivable, not hand-maintained per project.**

### A2. Jira Service Management / ITIL request types

- **Taxonomy** [documented]: Incident (restore service), Problem (root cause, separate record), Change (Standard / Normal / Emergency), Service request. Incident→Problem is a *link plus a new item*, not a state change — the same shape redkiln uses when an incident spawns a follow-up initiative.
- **Selection**: request type chosen at intake (portal form or automation); change *type* selected by risk. Emergency changes deliberately **skip** CAB stages [documented, see A5].
- **Activity catalog**: post-incident review is its own request type with a template, i.e. the "activity" is modelled as *another item type*, not as a stage inside Incident [inferred from JSM PIR docs; generic ITIL].

### A3. Azure DevOps process templates (Basic / Agile / Scrum / CMMI)

1. **Taxonomy** [documented]: Basic (Epic/Issue/Task); Agile (Epic/Feature/User Story/Task/Bug/Issue/Test Case…); Scrum (Epic/Feature/PBI/Task/Bug/Impediment…); **CMMI: Bug, Change Request, Epic, Feature, Issue, Requirement, Review, Risk, Task, Test Case** — Change Request "for proposed changes to work products under change control", Issue "events that might block work", Risk "probability and variance", Review "design/code review record" ([CMMI artifacts](https://learn.microsoft.com/en-us/azure/devops/boards/work-items/guidance/cmmi-process?view=azure-devops), [choose a process](https://learn.microsoft.com/en-us/azure/devops/boards/work-items/guidance/choose-process?view=azure-devops)).
2. **Stage model** [documented]: per-WIT state lists; CMMI states Proposed → Active → Resolved → Closed with **state categories** (Proposed/In Progress/Resolved/Completed/Removed) that let cross-template reporting normalise ([CMMI workflow](https://github.com/MicrosoftDocs/azure-devops-docs/blob/main/docs/boards/work-items/guidance/cmmi-process-workflow.md)). The **category** abstraction is worth copying: each kind has its own states but every state maps to a shared category so dashboards and gates can be written once.
3. **Activity catalog**: none; the closest is the **Activity field** on Tasks (Deployment, Design, Development, Documentation, Requirements, Testing) — a *label*, not an executable [documented, Agile/CMMI field reference].
4. **Selection**: **template chosen at project creation**, then **inherited process** customisation (add WITs, states, rules; rules can set fields on transition, but there is no scripting) [documented]. Behaviour = data model + UI, not an engine.
5. **Re-entry**: states are free-form; no artifact awareness.
6. **Complaints** [inferred from common docs/forum patterns]: template choice is near-irreversible ("you can change process, but only within the same family"), CMMI's ceremony is heavy so almost nobody uses Review/Risk WITs as intended; Basic is what most teams end up in. The interesting evidence is the *existence* of Risk/Review/ChangeRequest as first-class kinds — a signal that when process rigour is required, people add **item kinds**, not stages.

### A4. GitLab work items

1. **Taxonomy** [documented]: the unified **work item** model with types Issue, Incident, Test case, Task, Objective, Key result, Epic, Requirement; `issue_type` moved to a `work_item_types` table explicitly "to allow users to define custom work item types in the future" ([work items dev docs](https://docs.gitlab.com/development/work_items/), [user docs](https://docs.gitlab.com/user/work_items/)). GitLab 18.10 replaces the Issues and Epics pages with **Plan > Work items**.
2. **Stage model** [documented]: Open/Closed plus **type-specific widgets** — Incident gets timeline, severity, SLA countdown, escalation policy, linked alerts; Test case gets the test-planning widget; Objective/KR get progress. GitLab's design is *widgets per type*, not states per type: the type decides which **capabilities are attached**, and the state machine stays trivial.
3. **Activity catalog**: none executable; incident-management features (paging, status page, post-mortem via issue template) are attached to the incident type [documented].
4. **Selection**: type chosen at creation (or promoted: issue → incident, issue → epic); "widgets" are a static type→feature table in code [documented].
5. **Re-entry**: promote/convert keeps history [documented].
6. **Complaints** [documented in tracker]: the migration to work items took years and left inconsistencies (e.g. importing typed items, [#393605](https://gitlab.com/gitlab-org/gitlab/-/work_items/393605)); custom types still not GA as of the docs read.
   **Lesson**: "type ⇒ attached capabilities" is the *widget* formulation of redkiln's "type ⇒ activities". GitLab keeps it static and in code; redkiln can make it data.

### A5. ServiceNow ITSM (incident / problem / change)

1. **Taxonomy** [documented]: Incident, Problem, Change (Standard = pre-approved template from a catalog, Normal = full assessment + CAB, Emergency = expedited, ECAB/duty manager), Request ([community](https://www.servicenow.com/community/itsm-forum/difference-between-normal-standard-and-emergency-change/td-p/3311231), [guide](https://faddom.com/servicenow-change-management-concepts-workflow-pros-and-cons/)).
2. **Stage model** [documented]: **Change Models** define per-type state flows (New → Assess → Authorize → Scheduled → Implement → Review → Closed for Normal; Standard skips Assess/Authorize; Emergency compresses to Authorize → Implement → Review). The model is a *data record* (state transitions + conditions + required fields), not code — the closest classic analogue to redkiln's per-kind stage table.
3. **Activity catalog**: catalog of **Standard Change templates** (pre-authorised procedures); **Risk Assessment questionnaire** whose scored answers (impact × likelihood × CI criticality) set the risk level, which then *selects the approval path* (Risk ≥ Medium ⇒ CAB) [documented in the guides above].
4. **Selection**: two-stage — human picks change type; **risk score deterministically routes** within type. This is the best classic example of "computed attribute → stage skip" and matches redkiln's size/risk dimension.
5. **Re-entry**: Standard changes are *proposed* as Normal first, then promoted to a reusable template after a successful history — i.e. the catalog grows from evidence [documented].
6. **Complaints** [documented]: ITIL heaviness; CAB as bottleneck; teams over-classify as Emergency to skip assessment (gaming), which is why modern practice ("Modern Change Management", [community](https://www.servicenow.com/community/developer-forum/modern-change-management/td-p/3372624)) pushes automated risk scoring and pre-approval. Gaming the classifier is a risk redkiln must design for (labels are cheap to set).

### A6. Linear and Shortcut

- **Linear** [documented]: Initiative > Project > Issue (+ sub-issues), team-level **workflow states** in categories (Triage, Backlog, Unstarted, Started, Completed, Canceled) — no per-type workflows; "type" is a label. **Triage** is a per-team inbox state that new external issues land in; **SLAs** attach deadlines by rule ([SLAs changelog](https://linear.app/changelog/2023-03-16-slas), [triage guide](https://www.issuelinker.com/blog/linear-triage)). Templates per team pre-fill issues. 2026: issues can be **delegated to agents** (agent works, human stays assignee) and agents attach "coding sessions" ([agents](https://linear.app/docs/agents-in-linear), [coding sessions](https://linear.app/docs/coding-sessions), [assign/delegate](https://linear.app/docs/assigning-issues)). Selection of *what the agent does* is entirely the agent's; Linear only routes.
- **Shortcut** [documented]: story **types Feature / Bug / Chore**, plus Epic/Milestone; type affects reporting and templates only; workflow states shared across types ([story types](https://www.shortcut.com/blog/how-to-use-story-types), [templates](https://www.shortcut.com/blog/introducing-story-templates-and-5-steps-to-get-started-ecb965fd8100/)).
- **Lesson**: the modern lightweight trackers *dropped* per-type workflows in favour of one workflow + labels + templates + SLA rules. They compensate with **triage as an explicit state** and **rules that fire on attributes**. redkiln's "Triage stage that assigns classification" fits this trend; its per-kind stage list does not, so must be *invisible* (derived) to feel modern.

### A7. GitHub (issues, projects, Copilot, Agent HQ, agentic workflows)

1. **Taxonomy** [documented]: org-level **issue types** (default Task, Bug, Feature; up to 25 per org), **sub-issues** (multi-level hierarchy), **issue dependencies** (blocked-by/blocking, up to 50 each), **issue templates/forms** (per-repo, can preset type + labels), all exposed in `gh` CLI ≥ 2.94 with JSON fields for automation ([about issues](https://docs.github.com/en/issues/tracking-your-work-with-issues/learning-about-issues/about-issues), [CLI changelog 2026-06-10](https://github.blog/changelog/2026-06-10-manage-sub-issues-types-and-dependencies-from-github-cli/), [dependencies preview](https://github.com/orgs/community/discussions/165749)). Redkiln's substrate exists natively; nothing needs a side-table.
2. **Stage model** [documented]: none on the issue (open/closed + reason). **Projects v2** adds a Status single-select and **built-in workflows** (item added/closed/merged → set status; auto-add by filter; auto-archive) — attribute-triggered rules, not a state machine ([built-in automations](https://docs.github.com/en/issues/planning-and-tracking-with-projects/automating-your-project/using-the-built-in-automations)). March 2026: **agent activity** shows on issues/projects ([changelog](https://github.blog/changelog/2026-03-26-agent-activity-in-github-issues-and-projects/)).
3. **Activity catalog**: three layers. (a) **Copilot coding agent**: assign an issue to Copilot → it opens a PR; **custom agents** are `.github/agents/*.md` (persona + tools + instructions) selectable in **mission control** ([Agent HQ](https://github.blog/news-insights/company-news/welcome-home-agents/), [mission control how-to](https://github.blog/ai-and-ml/github-copilot/how-to-orchestrate-agents-using-mission-control/)). (b) **GitHub Agentic Workflows (gh-aw)**: a Markdown file in `.github/workflows/` with YAML frontmatter (triggers incl. `issues: labeled`, permissions, safe-outputs like `create-issue: assignees: [copilot]`, engine: Copilot/Claude/Codex/Gemini) compiled to a `.lock.yml` Actions workflow ([docs](https://docs.github.com/en/copilot/how-tos/github-agentic-workflows/creating-github-agentic-workflows), [gh-aw](https://github.com/github/gh-aw), [site](https://github.github.com/gh-aw/)). (c) **Copilot Spaces / instructions / AGENTS.md** for context.
4. **Selection**: **human-chosen** (assign Copilot, pick custom agent) or **event-triggered** (gh-aw `on: issues: types: [labeled]` with an `if` on the label). There is *no* type→agent mapping product feature as of Sept 2026: the mapping is whatever you encode in a gh-aw frontmatter `if:` or an Actions matrix [documented + inferred]. Agent HQ is a **fleet console**, not a workflow engine — the how-to's advice is "write a strong prompt, pick a custom agent, watch logs, steer".
5. **Re-entry**: Copilot coding agent restarts from the issue + PR comments; sessions are logs, not resumable plans [documented in mission-control post].
6. **Complaints** [documented/inferred]: issue types are org-only (no per-repo types; no types on personal repos); dependencies are preview; Projects automations race (auto-archive vs item-closed, [devactivity](https://devactivity.com/insights/optimizing-your-software-project-tracking-navigating-github-projects-auto-archive-race-condition/)); mission control drift/scope-creep monitoring is manual. **Opening**: GitHub gives redkiln every *noun* (type, sub-issue, dependency, label, agent) and no *verb* that turns type into a plan.

## B. AI SDLC frameworks

### B1. BMAD-METHOD v6

1. **Taxonomy** [documented]: no item kinds; instead **planning tracks** by scale: Quick Flow (levels 0–1: bug fixes, small features, refactors, "prototyping and spikes"; 1–15 stories), BMad Method (10–50+ stories), Enterprise (30+; compliance) ([scale-adaptive planning](https://www.mintlify.com/bmad-code-org/BMAD-METHOD/concepts/scale-adaptive-planning), [DeepWiki routing](https://deepwiki.com/bmadcode/BMAD-METHOD/4.2-context-engineered-development-(ide))).
2. **Stage model** [documented]: four phases Analysis / Planning / Solutioning / Implementation with a **conditional-phase table** per track (Analysis: Skip / Optional / Recommended; Solutioning: Skip / Architecture+Epics / +Integrations; Implementation: quick-dev / story-by-story / +quality gates). Artifact granularity and ceremony level also scale per track.
3. **Activity catalog** [documented]: ~12 agents (analyst, PM, architect, SM, dev, QA/TEA…), ~30+ workflows as slash commands (`/bmad-bmm-quick-spec`, `-quick-dev`, `-create-prd`, `-create-architecture`, `-create-epics-and-stories`, `-sprint-planning`, `-create-story`, `-code-review`, `-retrospective`, `/bmad-help`, `workflow-init`, `workflow-status`), plus TEA module. Exact count varies by module install; treat "~30 workflows, ~12 agents" as approximate [inferred from docs listing].
4. **Selection** [documented]: **LLM-assessed with human confirmation**. `workflow-init`/`/bmad-help` recommends a track from a conversation; **scope-detection guardrails** inside quick-spec/quick-dev raise a "SCOPE ALERT" and recommend escalation; user may "Proceed anyway". Manual override by invoking a track's entry workflow directly. Escalation ("tech-spec becomes input to the PRD") and de-escalation ("convert PRD to tech-spec") are first-class.
5. **Re-entry** [documented]: `workflow-status` reads a status file to tell you where you are and what's next; artifacts carry forward on escalation. No hashing/skip logic: "already has a PRD" is detected by the LLM reading files [inferred].
6. **Complaints** [documented]: heavy for narrow fixes, token cost because each stage reloads planning context ([dev.to comparison](https://dev.to/willtorber/spec-kit-vs-bmad-vs-openspec-choosing-an-sdd-framework-in-2026-d3j), [HackerNoon showdown](https://hackernoon.com/the-spec-first-development-showdown-spec-kit-openspec-bmad-and-gangsta-agents-compared)); v4→v6 churn; many agents/personas to learn.
   **Closest competitor on "selection".** BMAD selects by *scale*, redkiln by *kind × scale*; BMAD selection is probabilistic (LLM reads the brief), redkiln's is deterministic (labels + engine). BMAD's *conditional-phase table* is the exact shape of redkiln's stage matrix.

### B2. GitHub spec-kit

1. **Taxonomy**: one kind — a *feature* (numbered branch `NNN-name`, `specs/NNN-name/`) [documented, [repo](https://github.com/github/spec-kit)].
2. **Stage model** [documented]: `/speckit.constitution` → `/speckit.specify` → (`/speckit.clarify`) → `/speckit.plan` → (`/speckit.checklist`) → `/speckit.tasks` → (`/speckit.analyze`) → `/speckit.implement` (+ newer `converge`) ([reference](https://github.github.io/spec-kit/reference/overview.html)). Fixed linear pipeline with optional quality gates; clarify does a "structured ambiguity scan across ten taxonomy categories, ≤5 questions".
3. **Activity catalog**: ~9 commands, all in the sequence; no bug/incident variants.
4. **Selection**: **human-chosen, fixed order**; the constitution is a static constraint checked by `analyze`.
5. **Re-entry**: re-running a command overwrites that artifact; downstream must be re-run by hand [documented in guides]. No skip-if-exists.
6. **Complaints** [documented]: waterfall-ish, greenfield bias, "too many artifacts for a two-line change"; brownfield needs OpenSpec ([LogRocket](https://blog.logrocket.com/github-spec-kit/), comparisons above).

### B3. Kiro (AWS)

1. **Taxonomy**: **feature spec** only; bugs are "vibe" chats or specs by convention [documented, [feature specs](https://kiro.dev/docs/specs/feature-specs/)].
2. **Stage model** [documented]: requirements.md (**EARS**: "WHEN … THE SYSTEM SHALL …") → design.md → tasks.md, each with an approve gate; tasks executed one by one from the tasks file.
3. **Activity catalog**: 3 spec phases + **agent hooks** (file save/create/delete/manual → run agent: tests, review, docs) + **steering files** with `inclusion: always | fileMatch (fileMatchPattern) | manual` ([steering](https://kiro.dev/docs/steering/)); 2026 adds skills, "powers", global steering ([Medium](https://medium.com/@Sanjjushri/advanced-kiro-steering-strategies-skills-powers-and-production-workflows-b68153ba88c2)).
4. **Selection**: **human** (spec vs vibe), **event** (hooks), **path-conditional** (steering fileMatch). No item-kind logic.
5. **Re-entry**: specs are files; re-opening a spec resumes at the unchecked task; requirements can be regenerated from an existing design ("spec from code") [documented in getting-started].
6. **Complaints** [documented]: rigid three-phase flow for small work; EARS verbosity; long spec generation ([codemyspec](https://codemyspec.com/blog/kiro-specs-explained)).
   **Lesson**: *conditional inclusion keyed on a declared attribute* (fileMatch) is Kiro's only selection primitive and it is data, not prompt. Generalise it: `inclusion: kind=incident` on an activity.

### B4. OpenSpec (Fission-AI)

- **Taxonomy** [documented]: a **change** (proposal.md + delta specs + design.md + tasks.md) against a living `specs/` tree; `changes/archive/` after merge ([concepts](https://github.com/Fission-AI/OpenSpec/blob/main/docs/concepts.md)).
- **Stage model**: explicitly "**actions, not phases**" — create / implement / update / archive, "fluid not rigid… no phase gates" [documented, README].
- **Catalog**: ~6 CLI/slash actions; selection **human**, order free.
- **Re-entry**: brownfield-first — delta specs are diffs against existing specs, so pre-existing artifacts are the *default* input, not an exception. Archive merges deltas into the spec baseline [documented].
- **Complaints** [documented]: lack of enforcement means drift; no built-in review/verification step (comparisons above).
- **Lesson**: OpenSpec's *delta-spec* is the best model for redkiln's re-entry: an activity should emit a delta against an existing artifact rather than a fresh artifact.

### B5. Agent OS v3 (buildermethods)

- v2 had spec → tasks → orchestrated implementation; **v3 retired implementation and orchestration phases** ("frontier models handle spec implementation well on their own — recommended approach in 2026+") and refocused on **standards injection** (`/inject-standards` into subagents, skills, commands) ([discussion #310](https://github.com/buildermethods/agent-os/discussions/310), [migration](https://buildermethods.com/agent-os/migration)).
- **Selection**: none; the human runs plan/spec commands; standards are always-on context [documented].
- **Reading** [inferred]: strongest counter-evidence to heavy orchestration for *implementation* of a single spec; it says nothing about cross-item orchestration (incident vs feature), which is where redkiln lives. Keep redkiln's engine at the *stage* level and let the harness own the inner loop.

### B6. obra/superpowers (skills as an activity catalog)

1. **Taxonomy**: implicit — "building something" vs "fix this bug" vs "review" [documented, README].
2. **Stage model** [documented]: the "basic workflow" is brainstorming → using-git-worktrees → writing-plans → subagent-driven-development | executing-plans → test-driven-development → requesting-code-review → finishing-a-development-branch ([README](https://github.com/obra/superpowers/)).
3. **Activity catalog** [documented]: **14 skills** in 4 groups — Testing (TDD), Debugging (systematic-debugging, verification-before-completion), Collaboration (brainstorming, writing-plans, executing-plans, dispatching-parallel-agents, requesting/receiving-code-review, using-git-worktrees, finishing-a-development-branch, subagent-driven-development), Meta (writing-skills, using-superpowers). Ships for 14 harnesses (Claude Code, Codex, Cursor, Devin, Factory Droid, Gemini CLI, Copilot CLI, Kimi, OpenCode, Pi, Hermes…). 283k stars — the de-facto standard catalog.
4. **Selection** [documented]: **LLM-chosen, prompt-enforced.** A session-start hook injects `using-superpowers`, which instructs: "check for relevant skills before any task — mandatory workflows, not suggestions"; process skills (brainstorming, systematic-debugging) run before implementation skills; re-injected after context compaction. No deterministic router; triggering depends on the SKILL.md `description` matching.
5. **Re-entry**: plans are files; executing-plans resumes from the checklist; no artifact-hash skip [inferred].
6. **Complaints** [documented]: skills silently not triggering when descriptions are weak; too many installed skills → unpredictable behaviour and latency; rigidity/"fossilised" process ([mindstudio](https://www.mindstudio.ai/blog/claude-code-skills-common-mistakes-guide), [Caulfield](https://mikecaulfield.substack.com/p/softerware), [knightli](https://knightli.com/en/2026/05/15/obra-superpowers-agentic-skills-framework/)); harnesses without post-compaction hooks lose the bootstrap (README, Hermes note).
   **Lesson**: superpowers proves the *catalog* (14 well-tested activities) but leaves *selection* to the model. That is exactly the layer redkiln should own deterministically — and redkiln can *consume* superpowers-style SKILL.md as its activity implementations.

### B7. Claude Code: Dynamic Workflows, skills, subagents, agent teams

- **Dynamic workflows** (GA 28 May 2026) [documented]: Claude writes a JavaScript orchestration script (`agent()`, `pipeline()`, `parallel()`, `phase()`), a runtime runs it in the background; 16 concurrent / 1,000 agents per run; resumable by replaying saved agent results (first agent whose prompt differs re-runs, plus everything after); scripts save to `.claude/workflows/` and become `/commands` with `args`; `/effort ultracode` lets Claude decide when to use one; `Date.now()`/`Math.random()` throw to keep replays deterministic ([docs](https://code.claude.com/docs/en/workflows), [blog](https://claude.com/blog/introducing-dynamic-workflows-in-claude-code), [InfoQ](https://www.infoq.com/news/2026/06/dynamic-workflows-claude-code/)).
- The docs' own comparison table ("who decides what runs next": subagents/skills = Claude turn-by-turn; agent teams = lead agent; **workflows = the script**) is the clearest vendor articulation of the *declared-vs-emergent* split redkiln cares about.
- **Selection**: **LLM-written plan, human-approved once** (approval card lists phases); no item-kind awareness; "No mid-run user input — for sign-off between stages, run each stage as its own workflow" [documented]. Complaints: token cost, "intern swarm" misuse ([Folkman](https://tylerfolkman.substack.com/p/claude-code-workflows-are-here-dont)).
- **Reading** [inferred]: Anthropic solved *replayable orchestration* and *artifact-keyed resume* (cache by prompt equality) at the script level. Redkiln's engine should produce the same replay guarantee from item metadata rather than from an LLM-authored script, and could *emit* a dynamic-workflow script as one execution backend.

### B8. Roo Code, Cline, Cursor, Devin, Factory, Jules, Amazon Q, Sweep

- **Roo Code Orchestrator (Boomerang)** [documented]: modes = Code / Architect / Ask / Debug / Orchestrator (+ custom modes with tool restrictions). Orchestrator decomposes a task, spawns subtasks in a chosen mode, each in its own context; parent gets only a summary ([boomerang docs](https://docs.roocode.com/features/boomerang-tasks)). Selection: **LLM picks the mode per subtask.** Complaints: cost aggregation and hierarchy visibility ([issue #5376](https://github.com/RooCodeInc/Roo-Code/issues/5376)). SPARC (Specification, Pseudocode, Architecture, Refinement, Completion) is a community preset of fixed modes ([gist](https://gist.github.com/ruvnet/a206de8d484e710499398e4c39fa6299)).
- **Cline** [documented]: **rules** (always-on or path-scoped context) vs **workflows** (`.clinerules/workflows/*.md`, invoked as `/name`, injected once as explicit instructions) — "stop adding rules when you need workflows" ([blog](https://cline.bot/blog/stop-adding-rules-when-you-need-workflows), [3.13](https://cline.bot/blog/cline-3-13-toggleable-clinerules-slash-commands-previous-message-editing)). Selection: **human** via slash. Same rule/workflow dichotomy as Kiro steering/hooks and Claude CLAUDE.md/skills.
- **Cursor** [documented, general]: rules (always / auto-attached by glob / agent-requested / manual) + Plan mode (plan → approve → execute) + background agents; no item taxonomy; selection human + glob.

Patterns:
- **Nobody combines all three of: item-kind taxonomy, executable activity catalog, deterministic selection.** Trackers have taxonomy + static state machines and no executable activities; AI frameworks have executable activities and either fixed order (spec-kit, Kiro) or LLM-chosen (BMAD, superpowers, Roo, dynamic workflows).
- **Every mature tracker abstracted "type-specific" behind a shared layer**: Jira schemes, ADO state categories, GitLab widgets, ServiceNow change models, Linear state categories. The abstraction is what keeps per-type divergence maintainable.
- **Only ServiceNow and BMAD compute a routing attribute** (risk score; scale level) and use it to skip stages; both retain a human confirmation. Both are gamed/complained about when the score is wrong.
- **Re-entry is nearly universally naive.** OpenSpec (delta specs) and Claude dynamic workflows (replay by prompt equality) are the only substantive answers; neither keys on *item* metadata.
- **Incident-specific flows exist only in ITSM tools and GitLab widgets** (timeline, severity, SLA, PIR); in AI tooling only Factory's retired Reliability Droid ever targeted incidents. Bug-specific flow = superpowers `systematic-debugging` (LLM-triggered) and BMAD Quick Flow (scale-triggered, not kind-triggered).

## D. Gaps and openings for redkiln

**Gap 1 — Deterministic per-item DAG from self-describing activities.** No system lets an activity *declare* `applies_to: kinds=[incident, bug], stages=[investigate]`, `requires: artifacts`, `produces: artifacts`, and then derives the plan. Superpowers/Kiro/Cline have the catalog but rely on description-matching or human slash commands; BMAD's conditional-phase table is hand-authored per track. Redkiln can make the table *emergent* from activity manifests: type + labels (+ size/risk) ⇒ stage list ⇒ activities whose predicates match ⇒ DAG ordered by artifact dependencies (Tekton-style edges from output references). This is the one differentiated primitive; everything else in the survey is a lookup table or a prompt.

**Gap 2 — Artifact-aware skip / re-entry keyed on the item.** Only OpenSpec (delta) and Claude workflows (prompt-equality replay) address it, and neither knows about issues. Redkiln can check, per activity, whether its declared outputs already exist for this item (sub-issue comments, PR, files in the item folder), hash their inputs, and **skip or run in delta mode**. This directly answers the BMAD complaint ("each stage reloads planning context") and spec-kit's overwrite problem.

**Gap 3 — Incident/bug-specific investigation catalog in an agent tool.** ITSM has the *record* shape (incident vs problem, severity, timeline, PIR) but no agent activities; AI tools have debugging skills but no incident semantics (stabilise-first, blast radius, rollback vs fix-forward, PIR spawning a follow-up initiative). A small catalog (reproduce, bisect, blast-radius, mitigation-vs-fix decision, rollback plan, PIR, spawn-problem-item) selected *by kind* is unoccupied territory — Factory retired the only attempt.

**Gap 4 — Escalation/de-escalation as data, not conversation.** BMAD's scope alerts are the right idea, implemented as LLM prose. Redkiln can implement "reclassify" as a label change that re-derives the DAG, preserving completed activities whose predicates still hold (Gap 2 makes this cheap).

**Gap 5 — Cross-harness catalog, single selector.** Superpowers ships one catalog to 14 harnesses; Claude/Kiro/Cline each own a selector. Redkiln can be the *selector* that consumes SKILL.md-shaped activities (adding a manifest sidecar for kind/stage predicates) and emits per-harness invocations (Claude subagent, gh-aw workflow, dynamic-workflow script) — the "missing link" several 2026 stack analyses name ([Dev Genius](https://blog.devgenius.io/the-agentic-coding-stack-7-tools-5-layers-and-the-missing-link-nobody-has-built-yet-de264b260db3)).

### Five concrete design lessons

1. **Put the per-kind divergence behind a shared abstraction, like every tracker that survived.** Model stages with *categories* (ADO state categories / Linear) so gates, dashboards and the GitHub Projects Status field are written once; kinds differ only in *which* stages and activities are instantiated, never in the vocabulary. Never hand-author "workflow per type per project" (Jira sprawl).
2. **Selection must be a pure function of item metadata, with a visible, editable override — and a classifier that is hard to game.** ServiceNow (risk score) and BMAD (scale level) both show computed routing works *and* gets gamed. Use type + labels + computed size/risk, log the derivation on the issue ("plan derived from: type=bug, size=S, risk=low ⇒ stages [...]"), and require an explicit label (`process:override`) rather than a conversation to deviate. Keep a "propose reclassification" activity (BMAD scope alert) that only *recommends*.
3. **Make activities self-describing (kind/stage predicates + typed inputs/outputs), and treat SKILL.md as the implementation format.** Catalogs classify by domain or owner, never by kind/stage; add that metadata as a sidecar and redkiln gains 4,000+ candidate activities for free while keeping selection deterministic. Description-matching is the documented failure mode of skills; don't rely on it for *whether* something runs, only for *how*.
4. **Re-entry = artifact check, then delta mode; steal OpenSpec's delta spec and Claude's replay-by-input-equality.** Every activity declares outputs; the engine hashes inputs (item body, labels, upstream artifacts, activity version) and skips on match, else runs with the existing artifact passed in as a delta baseline. This is what makes reclassification, resume-after-crash, and "already has a PRD" all one mechanism.
5. **Keep the engine at stage/activity granularity; let the harness own the inner loop.** Agent OS v3 retired implementation orchestration because frontier models do it well; Claude dynamic workflows, Roo Orchestrator and superpowers SDD all own within-activity fan-out. Redkiln should decide *which* activities run and *what artifacts* they must produce, then delegate execution (Claude subagent, gh-aw workflow, dynamic-workflow script), and provide the incident/bug-specific catalog that no harness ships.
