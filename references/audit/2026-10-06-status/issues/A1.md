TITLE: Wire the Ctrl-C/SIGTERM CancelToken into the run verb
LABELS: bug
STATUS: untracked

## Finding
`main` installs the `ctrlc` handler and then drops the token it returns. `verbs::run` builds its own fresh `CancelToken`, which nothing ever fires. The handler therefore cancels a token no reader holds, so Ctrl-C/SIGTERM never reaches the adapter (`Cancelled { by: Signal }`, exit 13) or the step-boundary check (exit 130).

## Evidence
- crates/rk-cli/src/main.rs:34-37 @ ce4ed1a, 62dd3b8: `Ok(token) => drop(token)`; the comment defers the readers to "Slice 3".
- crates/rk-cli/src/signal.rs:48-50 @ ce4ed1a: `install()` returns the token whose clone only the handler holds.
- crates/rk-cli/src/verbs/run.rs:398 @ ce4ed1a, 62dd3b8: `let token = CancelToken::new();` (unconnected to `signal::install`). The checks at run.rs:1329/1341/2763 read this orphan token.
- No other `signal::install`/`set_handler` call site exists (git grep over crates).
- Records: no entry in s8j-run-preparation.md, s8-exit-criterion.md or PROGRESS.md owns the wiring. s8-exit-criterion.md:113 and s8j-run-preparation.md:1549-1583 kill runs with `taskkill /T /F`, bypassing the handler.

## Impact
A paid `redkiln run` cannot be interrupted gracefully: no `step_cancelled` row, no exit 13/130, and containment teardown depends on the process dying. The kill-mid-run checks in Step 8 hide this. The child's own behaviour on Windows Ctrl-C is unverified.

## Suggested fix
Pass the token from `signal::install()` into `run` (an argument or a field on the verb context) and delete the `CancelToken::new()` at run.rs:398. Make the `signal_during_dispatch_is_cancelled_by_signal_exit_13` test drive the real entry point rather than a token it builds itself.
