TITLE: Scrub provider environment variables in the rk-cli test harness
LABELS: bug
STATUS: untracked

## Finding
The rk-cli integration tests spawn the `redkiln` binary through one constructor that removes only `REDKILN_LAUNCH_RECORD`. The product deliberately refuses `ANTHROPIC_*`/`CLAUDE_*` credential variables (ADR-0010; the one denylist in rk-adapter-claude). A developer or CI shell that exports one makes about 61 tests fail for reasons unrelated to the code under test.

## Evidence
- crates/rk-cli/tests/it/main.rs:288 @ ce4ed1a and 62dd3b8: `cmd.env_remove(rk_cli::env::LAUNCH_RECORD);` is the only scrub in `redkiln_command` (lines 270-292). The 62dd3b8 diff of this file (long temp path, git maintenance off) leaves it unchanged.
- crates/rk-cli/src/env.rs:55 acknowledges the hazard for `Env::from_map`, but the process-spawning tests do not apply it.
- Audit run: 61 failures with `ANTHROPIC_BASE_URL` set (appendix §8; log-test-cleanenv.txt).
- Records: PROGRESS.md:635-636 record a workaround (`env -u ANTHROPIC_FOUNDRY_API_KEY bash`) for checkpoint blocks. No record owns a hermetic harness.

## Impact
"Green" depends on the invoking shell. The author's box has `ANTHROPIC_FOUNDRY_API_KEY` set at user scope, so a clean run is a manual step, and CI or a contributor with a provider variable sees spurious reds.

## Suggested fix
In `redkiln_command`, call `env_remove` for every name in `rk_adapter_claude::env_denylist`, plus any variable with prefix `CLAUDE_` or `ANTHROPIC_`. Add a test that sets one in the parent and asserts the child's launch gate is unaffected.
