## Blocker A

**Blocker.** §8c.1 rule 2 ("Any other non-empty line in the region refuses.") refuses the sixth libtest golden, crates/rk-adapter-toolchain-rust/tests/fixtures/libtest/1.98.1/this-repository.stdout (rc 0, green). They leak from crates/rk-cli/tests/it/doctor.rs:1946, `rk_cli::verbs::doctor::run(`, which is the only in-process verb run call under any tests/. It writes through `std::io::stdout()`, which libtest capture does not intercept. The same call appears in six verb files: catalog, cost, doctor, explain, lint and status. With those 39 lines skipped, the tally is 784/0/9 over 44 blocks, which is Checkpoint 8b's reading. §8c.1 says: "If the parser refuses it, the stage stops. **Ruling.**
PROVISIONAL, carried by record T (ADR-0169), written proposed: option (1) narrowed, with the leak fix deferred. If record T is flipped, the ruling is undone by deleting one parser branch and one clause of T.

A. Parser rule change (libtest_lines.rs, libtest path only). Inside a block's RECORD region, a non-empty line that matches neither the record grammar `^test (.+) \.\.\. (ok|FAILED|ignored(, .*)?)$` nor the slow-test notice is a FOREIGN line. It is skipped and never counted. Everything else in §8c.1 is unchanged:
- the region still ends at the first empty line;
- the slow-notice name cross-check still refuses on a name the block does not record;
- rule 3 (header count and summary passed/failed/ignored agreement), rule 4, rule 5 (--list) and rule 6 (exit-code agreement, including UnattributedFailure) all still refuse;
- a record-grammar line outside a block is still never counted.

B. Visibility, so the skip is never silent:
- `Tally` gains `foreign_lines: u32`, plus the first foreign line's 1-based line number and text as evidence.
- The adapter carries `foreign_lines` onto the report's runner evidence. It is a count from the parser, not parsed prose (AC-329).
- this-repository.tally.json pins passed 784, failed 0, ignored 9, blocks 44, foreign_lines 39 and first_foreign_line 287.

C. Golden. this-repository.stdout is committed exactly as captured in P1, 39 RK-D lines included. It is not re-captured.

D. P3 tests. Each test goes red against the strict parser or against the named mutant before it goes green.
1. The sixth golden parses to Ok(784/0/9/44, foreign_lines 39). It is red under today's strict rule 2.
2. A synthetic region with one extra leaked `test x ... ok` line refuses by count (rule 2's header count).
3. A synthetic region where a leaked fragment corrupts a FAILED record into an unmatched line, plus a leaked ok record, refuses by rule 3 (summary disagreement) and, at non-zero exit, by rule 6.
4. A leaked empty line mid-region refuses. The region closes early and the count falls short. This is a pinned fail-closed false refusal.
5. A slow notice naming an unrecorded test still refuses.

Mutants:
- one that drops the header-count check;
- one that drops the summary-agreement check;
- one that counts foreign lines.

Each mutant must be killed by at least one of tests 1-5 (take the next free M-numbers).

E. Scope limits:
- The nextest parser stays strict. The leak never reaches the status stream, and this ruling does not touch it.
- The rk-cli `std::io::stdout()` leak is NOT fixed in s8c. It goes to §8c.12 as a handed-on, unassigned s7d-hygiene item.

F. Record T records how it reads D21-43 N4. "Unparseable output is Unverifiable, never green" binds the protocol lines the tally is taken from: headers, records, slow notices and summaries. Each of those must parse and agree, or the block is Unverifiable. Foreign lines contribute nothing to any count. T flags this reading for the operator's flip as a deliberate interpretation of N4, not a silent one.

## Blocker C

**Blocker.** On the pinned tool versions, neither scan tool reports its advisory-database commit when run offline. Measured by P1: cargo-audit 0.22.2 run with --json --no-fetch returns database.last-commit = null, for both the real ~/.cargo/advisory-db and the fixture db. cargo-deny 0.20.2 run with --offline --format json check advisories --audit-compatible-output has no database member at all. So §8c.4's rule "The database commit is read from the report's own database member, and if the installed tool emits no such member, the scan refuses by name" makes sca_scan refuse on every run. That blocks the sca_scan handler, blocks verbs::sca_scan_records_the_advisory_database_commit, and leaves s8g's sca-scan unable to pass.

**Ruling.**
PROVISIONAL: take option (1'), which is option (1) with the panel's before/after check and hardening. All three judges converged on it (scores 8.5, 9 and 8). Record V (ADR-0170, written proposed) states it as a deviation.

1. PINNED PATH PER TOOL. The adapter never relies on a tool's default database location. Each tool gets an explicit path.
   - audit: `cargo audit --json --no-fetch --db <audit_db>` (plus `--file <Cargo.lock>`, as already specified).
   - deny: the adapter generates a deny config whose [advisories] db-path is a dedicated parent directory, <deny_db_parent>, written with forward slashes on Windows. It runs `cargo deny --offline -L debug --format json check advisories --audit-compatible-output`. deny opens `<db-path>/advisory-db-<url-hash>`, so the adapter does not work out that hash. It requires exactly one child directory under <deny_db_parent> and refuses by name if there are zero or more than one. It then reads deny's stderr DEBUG line "Opening advisory database at '<path>'", which is pinned per deny version the way the libtest goldens are, and requires that path to equal the child it reads HEAD from. If the line is missing or names a different path, the scan refuses by name. V states that this log-line check pins the path only. It never reads the commit from the line.

2. COMMIT SOURCE. For each database, the adapter reads HEAD through a single shared read-only rk_git head-read function built on gix. It reads once before its tool runs and again after the tool exits. The package handler's HEAD read, which §8c.4 already flags, uses the same function, so one guard-(6) amendment covers both reads.

3. REFUSE BY NAME, with a distinct name for each case, and never record a ScanReport in any of them:
   (a) the path is not a git checkout, or its HEAD does not resolve;
   (b) the before and after HEADs differ ("database moved mid-scan");
   (c) a non-null report member (audit last-commit) disagrees with the adapter's HEAD. The member is cross-checked, never allowed to overwrite the adapter's read;
   (d) the deny db-path child count is not exactly one;
   (e) deny's "Opening advisory database at" line is missing or names a different path.
   §8c.4's intent, that an unknown or moving database is never recorded, is kept. What changes is where the commit comes from.

4. RECORD SHAPE UNCHANGED. For each tool the report records {name, version, local db path, commit}, two entries (D21-42 6a; §8c.4 "The two databases are two pins"). Unrated advisories are still never counted as 0. Everything stays offline, with no fetch anywhere, so golden constraint 8 holds.

5. CVSS. Both tools give a per-advisory cvss, either a vector or null. A null counts as unrated. Scoring a vector needs a scorer, and V names it: the RustSec `cvss` crate, dual-licensed MIT OR Apache-2.0, both of which deny.toml's allow list already contains, so no licence amendment is needed. The alternative is in-tree v3.1 base-score code. The builder records which one landed, and if it is the crate, confirms its licence and its transitive licences with cargo deny check licenses.

6. TESTS (red first). The tests work at a short temp path. They copy tests/fixtures/advisory-db/db twice, git-init each copy and give the two copies DIFFERENT commits. One copy is audit's --db and the other is the only child of deny's db-path. The expected hashes come from an independent `git rev-parse HEAD` via the git CLI, not rk_git. verbs::sca_scan_records_the_advisory_database_commit asserts audit gets commit A and deny gets commit B, which kills a constant commit, a swap between the tools, and a read of ~/.cargo. Add refusal tests for a non-git db dir, a deny db-path with two children, and a before/after move. For the move, a test seam can move HEAD between the two reads. If no seam is admissible, V states that case as asserted by unit test of the comparator only.

Option (2) is rejected: it makes the D21-42 6a ScanReport demand unmeetable on the pinned versions. Option (3) is rejected: it breaks golden constraint 8 and §8c.4's offline rule, adds network, moves the shared ~/.cargo db, and still leaves deny without a commit.

**Why.** D21-42 6a is accepted ledger text, and it requires only that "the advisory-DB commit is recorded". It does not say where the commit comes from. The rule that the commit be "read from the report's own database member" is stage-file text, and §8c.4 itself says "record V fixes [the scan's semantics] so that the two files agree". ## Blocker D

**Blocker.** The pinned tsc's exit statuses do not match the Node build mapping in §8c.2. tsc 5.9.3 --noEmit exits 2 for diagnostics of every kind, including config errors, and exits 1 for a CLI or project error that means nothing was checked. Through pnpm, every failure collapses to 1.

**Ruling.**
Take option (1). Keep (3) only as record-T prose, with no runtime launcher refusal. Add the panel's discriminating no-tsconfig fixture.

Record T (ADR-0169, proposed) fixes the Node build outcome for the pinned tsc 5.9.3, run as `<program> tsc --noEmit` with program = DEFAULT_PROGRAM (npx.cmd on Windows, npx elsewhere):
- Exit 0 is Ok(BuildReport { status: passing, errors: 0 }).
- Exit 2 is Ok(BuildReport { status: failing, errors ≥ 1 }). This covers type errors, syntax errors, a tsconfig that is not JSON, an unknown tsconfig option, and TS18003 "no inputs". Record T states in plain words that a broken tsconfig reads as a failing build, never a passing one. `errors` is the count of `error TS<n>` diagnostic lines, with a floor of 1 under exit 2.
- Exit 1 is Err(NonZero), meaning cannot-run. Measured causes: an unknown CLI option, -p naming a missing project, and a directory with no tsconfig.json, where tsc prints its help and checks nothing. tsc's own source labels 1 `DiagnosticsPresent_OutputsSkipped`, returned on commandLine.errors.
- Any other non-zero status is Err(NonZero). Spawn, timeout and kill are Err, as for `test`.

Record T's evidence carries four more things:
- the P1 direct and npx.cmd readings, and the panel's no-tsconfig probe (rc 1, help text);
- the pnpm collapse (type error, CLI error and missing project are all 1), with a note that under this mapping the collapse fails closed to Err and never reads green;
- the statement that the mapping holds for the npx or direct launcher only. It extends DECISIONS-2026-09-09 #34's no-pnpm-forwarding ruling from `test` to `build` by citation, and adds no new code gate;
- the note that the POSIX `npx` pass-through (Linux CI) is unmeasured, and that the mapping belongs to the pinned tsc version.

Code: in the Node adapter's `build`, one match arm on the exit status: 0 gives passing, 2 gives failing, anything else gives Err(NonZero).
